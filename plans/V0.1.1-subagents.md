## #8 and #9 no longer check the same thing — DECIDED

They did. #8's *Runs* had the writer re-read its draft for *"each enumerable section's entries match
its CSV row for row"*, and #9's structural half asked the same question one step later, which is why
it was being sent every CSV. Neither entry mentioned the other.

**The row was two questions wearing one sentence.** Separating them settles it:

| The question | Whose | Why |
|---|---|---|
| **Is every declared section present at all?** | **#9** | Answered from `scope.deliverables` against the draft. Needs no CSV — and it is already list 2 of the three this agent reads the draft against |
| **Does each enumerable section match its CSV row for row, and is each name a link?** | **#8** | It renders those sections *from* those files, so the check costs nothing and it can fix what it finds |

Three things decide it and they point the same way:

- **Cost.** #8 is holding the CSVs anyway. #9 would be sent them for this and nothing else.
- **Ability to act.** #8 corrects a mismatch on the spot, holding the file that says what the right
  answer is. #9 can only report, and its findings land in `audit.md` under Unanswered — the bucket for
  *evidence the run never gathered*, which is the wrong home for *this table is short two rows* and
  prompts no repair.
- **What #9 is for.** It exists to catch a report that answers a question nobody asked, which is why
  its *Rule files sent* already excludes the command's reference file — *"it would bury the thing it
  exists to catch."* Conformance checking walks that exclusion back in through a side door.

So #9's *Data files sent* is the draft and nothing else, which is what it was before the row-for-row
check was briefly moved onto it.

## Checking the files a run writes — DECIDED

**No new checker in V0.1.1. The agents check their own output by reading it.** Peter: *I don't want
to do this extra validation in this version, it's too much — let the subagents just do prose
validation, like we planned originally.*

**What went wrong here, recorded so it is not re-proposed.** `validate.mjs` reads JSON against a shape
and nothing else, so it can check a return or a JSON file and cannot check a CSV or a markdown
document. Three entries were written saying #7, #8 and #10 each end by running it on one. They could
not. A separate text checker was proposed and is not being built.

**So the format rules stay with the agents that were already doing them**, as prose checks:

| Rule | Whose |
|---|---|
| a CSV cell has a source or `—`, no row without evidence, `url` points at the thing | #7, on the CSVs it writes |
| an enumerable section's entries match its CSV row for row, and each name is a link | #8, which renders them |
| no citation lost when a duplicate is deleted | #10, which deletes them |
| every declared section is present at all | #9, against `scope.deliverables` — the row-for-row half is #8's, above |

**Three of the four prevent a failure; #10's only records one.** The other three ask an agent to
compare what it wrote against a file that says what the right answer is, and it can fix what it
finds. #10's asks it to notice that its own deletion took the last citation with it — the thing it
just failed to notice. What makes that acceptable is not the check: it is that #10 reports every
removal by `claimId`, so a citation lost there is traceable in `audit.md` afterwards even when the
pass misses it.

**These are not deterministic gates, and the file should not imply they are.** An agent reading its
own output is the method `Deterministic vetting` says does not count — and V0.1's own design already
records that the deterministic-gate promise is unmet, every gate being the model following
instructions. This changes nothing about that position; it declines to improve it in this version.

**`validate.mjs` is untouched** and keeps the job it can do: JSON returns and JSON files against the
shapes in `subagent_returns.json` — `page-claims`, `source-handles`, `source-players`,
`source-raw-report` and the rest.

**TO BUILD — `claim_index.json` gets a shape and is checked.** Peter. It is JSON, so this needs no new
machinery: a `claim-index` entry in `subagent_returns.json`, validated as a file rather than as a
return, exactly like `page-claims` and `source-raw-report`. #7 runs it after writing, one repair
attempt, then the failure goes on its receipt.

**It is the one file worth checking most.** Everything after #7 depends on it — #11's dispatches are
built from it, the claim texts split #8's paragraphs, and every verdict joins back through its
`claimId`. A malformed index is not a bad section; it is a fact check that silently checks nothing.
It is also the only new file in the run that a script *can* check, which is why it gets one while the
CSVs and the summary do not.

**Four other contradictions were found in the same sweep and are fixed in place:** a refuted claim had
no route to `audit.md` (now written onto the loser in `claim_index.json`), #7's deleted unsourced
claims had none either (now on its receipt), the citation's file pointer named the claims file rather
than the page (now `cachedPage`, pointed at the page), and the new `audit.md` list read as the whole
file
rather than as a replacement for its verification half.

It is also the one context that has to survive all six phases, while a sub-agent's dies the moment
it returns. That asymmetry is why the bulk material goes to disk and only receipts come back.

### The stuck-agent check — BUILT

Applies to every agent here, so it sits at the top rather than in one entry.

**The trigger is the heartbeat's modification time, not time since dispatch** — two minutes without
it moving, and ten for the kill. A live agent is never killed for being slow, only for having
stopped. Time since dispatch said nothing useful: an agent twenty minutes into a long branch whose
heartbeat moved ten seconds ago is working, and one that fell over after thirty seconds is not.

**Two minutes is the default because the open web is the slow case** — a request working through its
backoff can honestly hold one line for three minutes, where every scripted source answers in about a
second. **A fast source may set a tighter threshold in its own `subagents/<agent>/<source>.md`, and
that wins for its sub-agents.** Hacker News is the first, at one minute.

### The run log — NEW

**DECIDED — the orchestrator writes one log for the whole run, at the topic root.** Peter: *a main
log with each sub-phase timing, so we can later debug what took longest.*

```
digmore/<slug>/run_log.md
```

At the topic root rather than in `cache/`, which is disposable — this is the only record of where a
run spent its time, and it is read after the run rather than during it.

**Two lines per step — `start` and `done` — each appended at the moment it happens.** The `start`
line goes in before the work, not held back until the step finishes: a run that dies in Vet has to
leave a log showing it reached Vet.

An excerpt — the run header and the first three steps. A real file carries a pair per step through to
`[6/6] Audit · done`, then the next run's header:

```
## run 2026-08-21T09:14:02Z — fresh · manual, full · run_history[0]

2026-08-21T09:14:02Z  [1/6]    Plan · start
2026-08-21T09:14:48Z  [1/6]    Plan · done — 1 scoping agent, 5 angles                     +46s
2026-08-21T09:14:48Z  [2.1/6]  Extract · Search · start
2026-08-21T09:19:30Z  [2.1/6]  Extract · Search · done — 25 branch searchers, 302 URLs     +4m42s
2026-08-21T09:19:30Z  [2.2/6]  Extract · Read · start
2026-08-21T10:31:11Z  [2.2/6]  Extract · Read · done — 188 page analysts, 12 blocked       +1h11m
…
```

- **The elapsed figure is the difference from the line above**, so nothing has to be kept in context
  and a partial log still reads correctly.
- **The step name is the marker `reporting.md` already prints**, so the log and the terminal never
  invent separate vocabularies.
- **A `done` line's tail says what the step did** — agents dispatched, and the one count that
  explains the duration. An hour is only debuggable beside the number of things it was doing.
- **Every sub-step gets its own pair**, including all eight inside Audit — review, repair,
  re-review, copy edit, both redrafts, fact check, record — and each wave of Enrichment's Player
  Profilers.
  That is where the time goes, and a single `Audit` line hides six dispatch groups and four
  rewrites of the deliverable. The log and the terminal use the same markers, so a conditional step
  that did not run is absent from both.
- **A failed or skipped step says so on its `done` line** — `Vet · done — Reddit and Twitter
  unavailable, no API key`. A missing pair reads as a crash, and a skipped phase is not one.
- **The timestamp comes from the shell, never from the model.** You have no clock, and a composed
  stamp makes every elapsed figure wrong. Append through Bash.
- **Append across runs, never replace.** Unlike `audit.md`, which describes one run, this is the
  record of what the topic has cost over its life — and the second run is when the first run's
  timings become useful.
- **Nothing reads it during the run.** It is a debugging artifact, not an input to a decision. The
  stuck-agent check still reads `cache/_progress/*.log`: different question, different time,
  different file.

Knock-ons in the skill: `phases/index.md` §"Where a run writes" gains a layout row and a writer row,
and `reporting.md` gains the rule that every marker it prints is appended here too.

### Resuming a run — read the log first — NEW

**DECIDED — a retry or a re-run reads `run_log.md` to find the phase it stopped in, and re-enters
there.** Peter: *check the main log for the last stage we were at and continue dispatching phases and
sub-agents from that stage — without bloating the orchestrator with files it does not need to read.*

Resume today infers position by comparing `research_plan.json` against the cache and every partial
output across all six phases — a scan of the whole topic directory, all of it into the context that
then has to survive the run. **The saving is the five phases you no longer scan**, not the one you
still do.

**The log gives you the phase; the disk gives you what is outstanding inside it.** Both, in that
order:

| Last line for a phase | What you do |
|---|---|
| `done` | re-enter the **next** phase, without opening the completed one's artifacts |
| `start` with no `done` after it | re-enter **that** phase and run its salvage path from `phases/index.md` |

The second row is why the log cannot replace the disk check: a run killed during Extract · Read wrote
`start` and nothing else, which names the phase and says nothing about which of 188 URLs were read.

**In Audit the same rule applies per sub-step**, since each writes its own pair — so a resumed run
re-enters at the review, the copy edit or the fact check rather than at the top of the phase. See
§"Resuming inside Audit", which is the one phase where that granularity matters.

**Three rules that keep it honest:**

- **No log, unreadable, or a topic predating this → full scan.** An absent log is no information,
  never evidence that nothing ran.
- **Where the log and the disk disagree, the disk wins.** These lines are written by you rather than
  by a script, so one can be wrong, out of order, or missing because the process died between the
  work and the write. A file that exists exists.
- **Record the resume decision as its own line**, naming the phase re-entered and whether it came
  from a `done` or an unfinished `start`. Otherwise a skipped four-second Extract and a broken one
  look identical.

**It changes nothing about what a phase does on re-entry** — the salvage paths already say how each
picks up. This decides *which* of them runs.

Knock-on in the skill: `phases/index.md` §"Salvage paths on phase failure" opens with the log, keeps
every per-phase path underneath it, and its closing *"Resume infers progress from on-disk state"*
becomes the two-source rule above.

## The Enrichment phase — NEW

**DECIDED — a sixth phase, between Vet and Synthesize.** Peter. The run becomes Plan, Extract, Vet,
**Enrichment**, Synthesize, Audit, and every progress marker renumbers to `[n/6]`.

The phase files are lettered, so two are renamed and one is new:

| Was | Is |
|---|---|
| `phases/synthesize_phase_d.md` | `phases/synthesize_phase_e.md` |
| `phases/audit_phase_e.md` | `phases/audit_phase_f.md` |
| — | `phases/enrich_phase_d.md` |

**BUILT — the phase exists and everything renumbered.** All three files are on disk under these
names, `brain/index.md` and `reporting.md` list six phases, and every marker reads `[n/6]`. What is
not built is part of what goes *inside* `enrich_phase_d.md` — see the TO BUILD below.

### Why it exists

Extract collects, Vet judges people, Synthesize writes. **Nothing between them turned what was
collected into the run's subjects** — and that gap is why `players.csv` had no owner: the only step
that ever enumerated players was `landscape.md` §2's inclusion cross-check, which counts mentions in the raw
report, a file the old #8 wrote in Synthesize — after #6 needs the rows. That is still true of #7's
raw report, which is why the count is a script's job here rather than a by-product of the writing.

Enrichment is the phase where the run works out **who this research is about**, using the verdicts
Vet has just produced. It cannot sit inside Extract — the verdicts do not exist yet. It cannot sit
inside Synthesize — the writer needs a finished file to render from.

### What happens in it

**Expert enrichment comes first, and everything after it counts what it added.**

1. **One #2 Branch Searcher per vetted expert**, in its Enrichment mode — an expert is a branch, and
   its source is implied by the handle. It reads that expert's vetting cache, ranks against the
   research question, and returns a URL list. No query: the material is already on disk.
2. **Dedupe**, against the other experts' lists *and* against what Extract already read — an expert
   surfaced because they said something the run read, so their cached comments overlap what is
   already extracted.
3. **One #3 Page Analyst per surviving page**, in its Enrichment mode: carrying the research
   question, keeping only claims that bear on it.
4. **One #4 Source Analyst per source that gained material**, in its Enrichment mode: append the new
   claims, entities and handles to that source's three files, leaving Vet's verdicts untouched.

**Then the player work, unchanged from what was already settled:**

5. **A script filters — `players.mjs candidates --topic <slug>`.** It reads all six
   `full_source_analysis/<source>-players.json`, joins every
   claim's `handle` to its verdict in `<source>-handles.json`, drops what the run does not listen
   to, recounts documents per player across all sources, and applies the 5+ floor. Deterministic:
   same inputs, same candidates, every run.
6. **The orchestrator selects.** It reads the surviving candidates — names, counts and the
   per-source relevance notes, **not claim text** — and decides which become rows.
7. **The orchestrator writes `players.csv`** with the rows and whatever base data it already has.
   Cells that need fetching stay empty.
8. **One #6 Player Profiler per row**, dispatched with that player's claim references.
9. **The orchestrator fills the returned cells** into the rows it already wrote.

**And that is where the phase ends.** The Raw report writer was step 10 here and is now the first
step of Synthesize — see §"Where the Synthesize / Audit seam falls". Enrichment answers *who the
research is about*; turning the evidence into documents is the next phase's job.

**TO BUILD — `enrich_phase_d.md` holds steps 5 to 9 and none of steps 1 to 4.** The phase file
exists and opens at the candidate filter, so the expert step is in no phase file at all: it is still
`synthesize_phase_e.md` §2, in the wrong phase and in the wrong order. The four steps above go in
ahead of the filter, and §2 is deleted with them.

**Why the expert work sits at the front.** It changes the claim set, and both the candidate count in
step 5 and the raw report in the phase after count it. Run it later — as `synthesize_phase_e.md` §2
still does — and its claims land after the candidate count and after the raw report, in a directory
nothing reads again. They would reach no report at all.

**Why the raw report waits for this whole phase.** #6 fetches pricing pages and funding announcements
— facts that exist nowhere else in the run and never become claims. A declared enumerable section
wanting a funding round it found could not see it. The raw report itself needs nothing from
`players.csv`; the enumerable sections do, and #7 builds those first.

**DECIDED — accepted, not solved: player-profile findings never enter the claim record.** Peter:
*players information is ranked before we start, and is scrutinised with claims, more online search
and more enriching — this data is quite robust.* Cells carry citations, but they are not claims, so
they are never scored, never ranked and never fact-checked. Recorded so the boundary of the
verification path is visible rather than assumed.

Later steps may be added to this phase; these are the ones settled now.

### Expert enrichment — what is on disk, per source

**DECIDED.** Peter. Selection is free everywhere, because vetting already fetched the material to
judge each expert by. Extraction is free only where that material is complete:

| Source | What vetting already cached | What Enrichment does |
|---|---|---|
| **Reddit** | up to 100 recent comments, full bodies, with subreddits and permalinks | select and extract straight from the cache — no fetch |
| **Twitter** | the sampled posts, **for deep-pass handles only** | expand on deep-pass handles only. Profile-only handles have no posts cached, and in `--fast` there is no deep pass at all |
| **Hacker News** | recent comments **in full**, each carrying the story it sits under | select and extract straight from the cache, and pull the surrounding thread when one is worth reading |
| **Blogs, personal sites, anything off-platform** | nothing | **out of scope.** Not expanded on |

**BUILT — the 280-character cut is gone.** It was ours rather than the API's: Algolia returned each
comment whole and `hackernews.mjs` sliced it before storing, throwing away for free the only thing
Enrichment needs to extract from. 280 characters is enough to judge whether a comment is on-topic and
not enough to quote from, so every usable comment would have cost a thread re-fetch to recover text
we already had.

**And `recent_comments` gained more than the missing text.** Each entry now carries `story_id` and
`story_title` beside the body, so following a comment to its thread needs no lookup — and the shape
matches Reddit's, one object per comment rather than parallel lists.

**BUILT — Hacker News is on Firebase and nothing about it is throttled.** Account age used to come
from the `news.ycombinator.com/user` HTML page at one request per 15 seconds. Firebase serves the
same fields unthrottled and in parallel; the page, its parser and its throttle are gone. Threads and
per-author searches were always on Algolia, which was never rate limited. See #5 for what that
changed in Vet.

**DECIDED — the new handles are not vetted.** An expert's post quotes someone the run has never seen.
Peter: *i am ok with no verdict handles that come from expert enrichment.* They are appended without
a verdict and quoted as unvetted.

One consequence, recorded rather than re-opened: the candidate script counts `unvetted` handles
toward the five-document floor, so the expert trail can now create a player on its own.

### What counts, and what is judgement

**Mechanical, in the script — the floor.** A player is a candidate at **5+ documents across all
sources**, counted after the claim filter. One document that names a player counts once, however
many times the name appears in it.

Which claims count:

| Handle verdict | Claims reach the report | Count toward the 5+ |
|---|---|---|
| `legit` | yes | yes |
| `unknown` | yes, caveated | yes |
| **`unvetted`** — no verdict exists: below `vet.handleCapPerSource`, or first seen in expert material after Vet finished | yes, caveated | yes |
| `promoter` | yes, labelled as a promotional signal | **no** |
| `spammer`, `throwaway` | no | no |
| **no handle at all** — websearch, local | yes, filtered on `pageQuality` | yes |

Three of those rows need their reasoning kept:

- **`unknown` and `unvetted` count.** An absent verdict means nobody looked, not that somebody
  rejected them. Excluding them would contradict #5's caveat decision, and on Twitter, where the
  heuristic floor never returns `legit`, no player could ever be counted from that source.
- **`promoter` is kept but not counted.** A founder posting about their own product across six
  threads is exactly how a promoter manufactures a player. The quotes still reach the report,
  labelled; they just cannot create a row on their own.
- **Claims with no handle count.** They are most of what is said about a company — vendor pages,
  comparisons, reviews — and #7's citation filter already judges them on page quality alone. Without
  them a company would be judged on forum chatter.

**The original brain was stricter than all of this**, and it is worth recording why we did not copy
it: §1 Filter there dropped every quote whose verdict was not `legit`, and dropped `forum` sources
from `unknown` handles outright. It also had **no vetting cap** — `vet_phase_b.md` says *"For every
handle seen in Phase A, run `vet_user`"* — so it never had unvetted handles to rule on.
`vet.handleCapPerSource` arrived during the V0.1 review, and #5 has since reversed the `unknown`
rule deliberately.

**Judgement, and whose.** The orchestrator decides **whether players are needed at all** and **which
qualifying candidates become rows**. It holds what that needs: `scope.deliverables` from Plan, the
command's reference file, and the ranked candidate list.

Three bounds on it, because an unbounded judgement here is the failure `Run ceilings` already
records — two real runs applying different caps because the number was prose the model was trusted
to obey, with nothing flagging the difference:

- It may **cut** from the qualifying list. It may **never add** a player below the floor.
- **Every exclusion is recorded with a reason.** `landscape.md` §2's inclusion cross-check already requires this and today
  has nowhere to put it.
- **A run whose declared sections need no players skips selection and profiling entirely.** That is
  the checkable form of "if at all": `gtm` writes no `players.csv` unless chained from a landscape
  parent, and `ask` has an explicit "no players in scope" path.

`enrich_phase_d.md` carries this framing and the inputs. It does **not** carry a per-command table —
`competitor` taking its focal company plus 3–5 nearest peers off the ranked list is one instance of
the judgement above, not a separate rule.

### No configured limit on the row count

**DECIDED.** Peter: *"no limit on row counts, our 5+ mentions and filtering of claim is a good
enough limit."* There is no `synthesize.playersProfiled`, and no `--fast` reduction. The floor plus
the claim filter are the bound, and unlike a fixed cap they scale with how much the run actually
found. This closes the open configuration question in #6.

### What it replaces

**`claims.mjs` is not built.** It was proposed to string-match player names across ~700 claims files
with a soft rule — name, aliases and domain as substrings — that could miss or over-match. Recording
the claim references in `<source>-players.json` at read time removes the matching problem entirely:
the association is written where the evidence is, by the agent that read it. Its two verbs are
absorbed, `entities` by #4 and `slice` by the enrichment script.

**Not to be confused with the query script over `claim_index.json`** (#7, #11). That one looks a claim
up by its `claimId` — an exact key written by the agent that created the claim. What was rejected here
is guessing an association after the fact by matching strings; looking one up by its own identifier is
the opposite.

## 11. Claim Fact Checker — was #13

- **Purpose:** Confirm that every claim in the finished report is supported by the text the run
  actually read, and name the ones that are not so they can be deleted.
- **Phase:** Audit `[6.6/6]`, after the copy edit and the marker redraft that follows it. The steps and
  their order are in §"Where the Synthesize / Audit seam falls".

### What this agent became — DECIDED

**It does not fetch anything, and it checks every claim rather than a ranked few.** Peter: *all
checks just do against our cache, don't refetch — it will be faster*, and *I want all claims in the
report to be checked … I don't want any unverified claim surviving the final audit stage.*

**The check is one question:** does the cached text we stored for this claim's source support the
claim? Nothing else. The text comes from `cache/<source>/`, written when Extract read the page, and
no request goes out.

**Why that is worth more than a live re-fetch.** A live fetch answers *does the page still say this*;
the cached comparison answers *did we read this correctly*. Only the second catches a fabricated
quote, and fabrication is the failure that matters — a claim invented during drafting, or a quote
attributed to a page that never carried it. And because a cached comparison costs a file read rather
than a request, it can run over **every claim in the report** instead of a top-ranked fifty.

**What is given up:** a dead link is not detected, and neither is a page edited since we read it. So
**"verified" here means the claim is supported by what we read — not that the URL still resolves.**

**DECIDED — no run says so, anywhere.** Peter: *the entire skill is built to not refetch; we don't
need to constantly mention it for every research in the audit.* It is a property of the design, not a
finding about a run. A disclaimer repeated every run costs the reader confidence to describe a
failure they cannot act on.

Peter: *when we get the link or post in the extract phase, this confirms the url is valid* — the
citation was live when the run collected it, and nothing rechecks it after.

### The unit of judgement is the paragraph, not the claim — DECIDED

**It reads the paragraph against its pages as one evidence set**, rather than pairing each sentence to
a `claimId` and checking them one at a time. Peter: *cross reference the text in the paragraph against
the text in the cachedPage belonging to the claim, and flag if there are any claims in the paragraph
that have no verification in the paragraph's cache.*

**It catches more than the claim-by-claim check did, and that is the point.** Checking per id only
ever examined text that carried a marker. A sentence #8 composed from nothing, with no id on it, was
invisible here — the design leaned on #9 to notice it, and #9 only asks whether a sentence *has* a
source, never whether the source says it. Asking of the prose instead of the bookkeeping closes that:
everything the paragraph asserts is held against everything the paragraph cites.

**It also dissolves the stale-marker case** rather than needing a rule for it. An id whose rendering
#10 removed simply never comes up, because nothing is looked up by id.

**What it loosens, recorded rather than discovered:** the evidence set is the union of the paragraph's
pages, so a sentence can be borne out by a page that arrived with a different claim in the same
paragraph. That is usually right — the paragraph's citations are the paragraph's evidence — but it is
a weaker standard than claim-against-its-own-source, and it is the one thing this change gives up.

**Two outcomes, not three:**

| Outcome | What it means | What happens |
|---|---|---|
| supported | the paragraph's pages bear the statement out | kept, and **not reported** — see the return |
| `unsupported` | nothing in them carries it | **the statement is deleted**, and named in `audit.md` |

`no-cache` is gone as a per-claim verdict. A page written in Extract does not go missing on its own,
so one absent file is a defect rather than a state to design around; the case that does happen is the
whole cache being gone, and that is the guard below.

**`unsupported` is not `refuted`.** Refutation is contradiction between two claims the run gathered,
it is decided by #7, and the loser is shown in "Refuted / unsubstantiated" as a finding. An
unsupported statement is a defect in us: nothing was contradicted, because there was nothing behind
it. It leaves no trace in the report at all. Same distinction as an unsourced claim — see #7.

**A guard on the missing cache, in three sizes.**

**One absent page — judge on the rest**, since a paragraph usually cites several. Nothing is reported
about the page itself: where its absence costs a statement, that statement comes back `unsupported`
and its reason says the cached page was not on disk, and where it costs nothing there is nothing worth
saying.

**All of a paragraph's pages absent — DECIDED, Peter.** There is no evidence to search, so every
sentence would come back `unsupported` and the paragraph would be deleted as though the report were at
fault. **Return no unsupported statements and say the evidence was unreadable.** The paragraph is
still deleted — nothing unverified reaches the user — but the orchestrator deletes it as *we could not
check this*, records that in `audit.md`, and tells #8's redraft the same. A defect in us is never
written down as a defect in the report.

**Most of them absent** means the cache was cleared or never written, and deleting everything it could
not confirm would ship an empty report that looks like a run that found nothing. Where the cache is
broadly absent the run stops and offers to start over — see §"When the cache is gone".

  say is there, and #9 passes it whenever it carries a link, because #9 asks only whether a fact has a
  source. So nothing between them ever opens a page to see whether that paragraph is true.

  **Every unmarked prose paragraph goes back, not a suspicious subset.** An earlier draft sent only
  those carrying a source link, on the grounds that a link without a marker is the contradictory case.
  That was the wrong instrument: it asks the orchestrator to guess which paragraphs *should* have been
  marked, and it misses the worse shape — a fabricated paragraph with no link and no marker, which
  reads as narration and asserts a fact.

  **The orchestrator detects, #8 judges.** Which paragraphs have markers is mechanical, and the
  orchestrator already holds the whole summary from step 1 and parses markers for step 3. Whether an
  unmarked paragraph *needed* one is a judgement about what the prose asserts, and only the agent that
  wrote it can make that. Same line the run draws everywhere else: the orchestrator decides what gets
  looked at, the agent decides what the answer is.

  **So the list is expected to be mostly innocent, and that is fine.** A section opener, a transition,
  a caveats line and `ask`'s Direct answer assert nothing that needs a claim behind it, and #8 says so
  and moves on. The cost of a wide list is one agent reading a few short paragraphs; the cost of a
  narrow one is a fabrication nobody sees.

  **One #8 redraft over the list, before any dispatch is built.** Same shape as every other repair in
  the run, and it must run first: a redraft after the fact check would produce paragraphs nothing had
  checked. Per paragraph #8 does one of three things — add the marker it forgot, cut prose that has no
  claim behind it, or confirm the paragraph asserts nothing and needs none. **One pass**; anything
  still unmarked is recorded in `audit.md` and left alone.

  **Prose paragraphs only.** Every row of an enumerable section is a link and none of them carries a
  marker, because a row is not a claim — it is rendered from a finished CSV. Sweeping those in would
  fire on every row of every `landscape` run.

  **The pairing is #11's, not the orchestrator's — DECIDED.** Peter. The orchestrator holds only the
  claim text; #11 holds the claim text, the quote and the cached page, so *"which sentence renders
  `claim-004`"* is a question only it can actually answer. Having the orchestrator guess first and
  #11 second-guess it is the same judgement made twice, the first time from the weaker position.

  It is the same line the run draws in Vet: the orchestrator decides **who** gets judged, the agent
  decides **what the answer is**. Which sentence carries a claim is the second kind.

  **What must still be checked is the sentence the user will read**, not the index's wording — #8
  phrased the claim in its own words and #10 may have rewritten it. That is why the paragraph goes
  over verbatim and the index's claim text travels beside it as the key, rather than as the thing
  being checked.

  **The marker floats; it does not have to sit on its sentence.** Peter. One comment per paragraph
  listing the ids in it — `<!-- claims: 001, 004, 009 -->` — is enough, which keeps #8's job simple
  and the document less cluttered.

  **Scope is what the markers say is there.** A claim #10 removed is not checked — it is not in the
  report. #8's and #10's returns describe what each of them did and are kept as records; nothing about
  scope is calculated from them.

  **A marker naming an id the paragraph no longer renders is skipped, not an error — DECIDED.** Peter:
  *I don't care for stale markers, they can remain — maybe later we will want to use them.* #10 can
  rewrite a paragraph and drop a rendering without saying so, leaving an id with nothing to check.
  There is nothing to verify and nothing to delete, so #11 reports it as not rendered and the
  orchestrator does nothing with it. **Do not build an error path for this**: an unrendered claim is
  out of scope by definition, and the guarantee is about claims the reader can see.

  **A refuted claim is in the report, so it is checked like any other — DECIDED.** #7 sends the loser
  to "Refuted / unsubstantiated" and #8 renders it, so it carries a marker and lands in a dispatch. That
  is right rather than incidental: refutation says another claim beat this one, and this check asks
  whether we read this one correctly in the first place. A loser that comes back `unsupported` is
  **deleted rather than displayed as refuted** — showing a reader that we investigated and killed a
  claim we in fact never had is the same failure as putting an unsourced claim in that section.
