## #8 and #9 no longer check the same thing — DECIDED

They did. #8's *Runs* had the writer re-read its draft for *"each enumerable section's entries match
its CSV row for row"*, and #9's structural half asked the same question one step later, which is why
it was being sent every CSV. Neither entry mentioned the other.

**The row was two questions wearing one sentence.** Separating them settles it:

| The question | Whose | Why |
|---|---|---|
| **Is every declared section present at all?** | **#9** | Answered from `scope.deliverables` against the draft. Needs no CSV — and it is already list 2 of the three this agent reads the draft against |
| **Does each enumerable section match its CSV row for row, and is each name a link?** | **#8** | It renders those sections *from* those files, so the check costs nothing and it can fix what it finds |

Three things decide it and they point the same way:

- **Cost.** #8 is holding the CSVs anyway. #9 would be sent them for this and nothing else.
- **Ability to act.** #8 corrects a mismatch on the spot, holding the file that says what the right
  answer is. #9 can only report, and its findings land in `audit.md` under Unanswered — the bucket for
  *evidence the run never gathered*, which is the wrong home for *this table is short two rows* and
  prompts no repair.
- **What #9 is for.** It exists to catch a report that answers a question nobody asked, which is why
  its *Rule files sent* already excludes the command's reference file — *"it would bury the thing it
  exists to catch."* Conformance checking walks that exclusion back in through a side door.

So #9's *Data files sent* is the draft and nothing else, which is what it was before the row-for-row
check was briefly moved onto it.

## Checking the files a run writes — DECIDED

**No new checker in V0.1.1. The agents check their own output by reading it.** Peter: *I don't want
to do this extra validation in this version, it's too much — let the subagents just do prose
validation, like we planned originally.*

**What went wrong here, recorded so it is not re-proposed.** `validate.mjs` reads JSON against a shape
and nothing else, so it can check a return or a JSON file and cannot check a CSV or a markdown
document. Three entries were written saying #7, #8 and #10 each end by running it on one. They could
not. A separate text checker was proposed and is not being built.

**So the format rules stay with the agents that were already doing them**, as prose checks:

| Rule | Whose |
|---|---|
| a CSV cell has a source or `—`, no row without evidence, `url` points at the thing | #7, on the CSVs it writes |
| an enumerable section's entries match its CSV row for row, and each name is a link | #8, which renders them |
| no citation lost when a duplicate is deleted | #10, which deletes them |
| every declared section is present at all | #9, against `scope.deliverables` — the row-for-row half is #8's, above |

**Three of the four prevent a failure; #10's only records one.** The other three ask an agent to
compare what it wrote against a file that says what the right answer is, and it can fix what it
finds. #10's asks it to notice that its own deletion took the last citation with it — the thing it
just failed to notice. What makes that acceptable is not the check: it is that #10 reports every
removal by `claimId`, so a citation lost there is traceable in `audit.md` afterwards even when the
pass misses it.

**These are not deterministic gates, and the file should not imply they are.** An agent reading its
own output is the method `Deterministic vetting` says does not count — and V0.1's own design already
records that the deterministic-gate promise is unmet, every gate being the model following
instructions. This changes nothing about that position; it declines to improve it in this version.

**`validate.mjs` is untouched** and keeps the job it can do: JSON returns and JSON files against the
shapes in `subagent_returns.json` — `page-claims`, `source-handles`, `source-players`,
`source-raw-report` and the rest.

**TO BUILD — `claim_index.json` gets a shape and is checked.** Peter. It is JSON, so this needs no new
machinery: a `claim-index` entry in `subagent_returns.json`, validated as a file rather than as a
return, exactly like `page-claims` and `source-raw-report`. #7 runs it after writing, one repair
attempt, then the failure goes on its receipt.

**It is the one file worth checking most.** Everything after #7 depends on it — #11's dispatches are
built from it, the claim texts split #8's paragraphs, and every verdict joins back through its
`claimId`. A malformed index is not a bad section; it is a fact check that silently checks nothing.
It is also the only new file in the run that a script *can* check, which is why it gets one while the
CSVs and the summary do not.

**Four other contradictions were found in the same sweep and are fixed in place:** a refuted claim had
no route to `audit.md` (now written onto the loser in `claim_index.json`), #7's deleted unsourced
claims had none either (now on its receipt), the citation's file pointer named the claims file rather
than the page (now `cachedPage`, pointed at the page), and the new `audit.md` list read as the whole
file
rather than as a replacement for its verification half.

### `uniqueBy` — nothing stops a list repeating a key — TO BUILD

**No shape in the run enforces one entry per thing**, and four of them are specified as if something
did. Found while asking whether `<source>-handles.json` could hold the same handle twice: it can, and
`validate.mjs` would pass it.

**`uniqueItems` is the wrong instrument.** In JSON Schema it means the whole item must be unique, so
two rows for `u/foo` differing in any field — a different `documentCount`, a different
`verdictReason` — both pass. What is needed is uniqueness **on a named key**:

```json
"handles": { "type": "array", "uniqueBy": "handle", "items": { … } }
```

**A new keyword, and the file already has one.** `requiredWhen` is non-standard and
`validateValue` implements it, so extending the vocabulary is the existing pattern rather than a new
idea. The array branch already handles `minItems`, `maxItems` and `items`; this sits beside them.

**Compare normalised** — lowercased and trimmed. `u/Foo` and `u/foo` are one person and two strings,
and `experts.mjs` already carries a `norm()` for exactly that. The error names both offending
indexes, because "there is a duplicate somewhere" is not a repairable message.

Where it applies, and one of them is load-bearing:

| Shape | Unique by | What a duplicate costs |
|---|---|---|
| **`claim-index`** | **`claimId`** | **the fact check joins on it — a duplicate id lands a verdict on the wrong claim.** This file is already named here as the one worth checking most |
| `source-handles` | `handle` | the handle is vetted twice, spends two slots of `handleCapPerSource`, and the verdict join answers from whichever row it meets first |
| `source-players` | the player's name | one entity's evidence splits across two rows and neither reaches the five-document floor |
| `page-analyst` | `url` | specced as one receipt per URL, enforced by nothing |

**Not `handle-vetting`** — that file holds one handle, so it has no array of handles to check.

**Why it matters most where no script writes the file.** The Source Analyst runs `no scripts, no
network` — the roster, the counts, the ranking and one-row-per-handle are all the model's own work
over 120 documents. Nothing sits between its judgement and the file except this check.

### The stuck-agent check — BUILT

Applies to every agent here, so it sits at the top rather than in one entry.

**The trigger is the heartbeat's modification time, not time since dispatch** — two minutes without
it moving, and ten for the kill. A live agent is never killed for being slow, only for having
stopped. Time since dispatch said nothing useful: an agent twenty minutes into a long branch whose
heartbeat moved ten seconds ago is working, and one that fell over after thirty seconds is not.

**Two minutes is the default because the open web is the slow case** — a request working through its
backoff can honestly hold one line for three minutes, where every scripted source answers in about a
second. **A fast source may set a tighter threshold in its own `subagents/<agent>/<source>.md`, and
that wins for its sub-agents.** Hacker News is the first, at one minute.

**TO BUILD — what a wrong kill costs is no longer one URL.** `phases/index.md` closes the check with
*"a wrong kill loses one URL rather than a batch"*, which was true when every agent held one item and
is not true of #3 any more: a killed Page Analyst now loses up to `extract.urlsPerDispatch` of them.
The paragraph is rewritten rather than deleted — killing a working agent is still the right trade,
because the alternative is detecting stuckness from a signal that does not exist — but it says the
real number and adds what follows from it:

- **Anything the batch already finished is on disk and stays there.** A Page Analyst writes each
  document's page and claims before it starts the next URL, so a kill costs the URL in flight and the
  ones not yet reached, never the ones behind it.
- **Every lost URL is recorded in `audit.md` under "dropped-for-budget" individually**, by URL, not as
  one line naming the dispatch. A batch recorded as a batch is a report that cannot say which four
  pages the run never read. **The heartbeat is what makes that possible** — its `url <n> of <n>` line
  is the only record of how far the agent got, and the entry for it is in #3's *Log file*.

### Every heartbeat line carries its own timestamp — BUILT

**DECIDED.** Peter. `runlog.mjs beat` appends the line unstamped, on the reasoning that *"the file's
modification time is the clock"*. That is true of the question it was written for — is this agent
stuck — and false of every other question anyone has asked the file since.

**What it cost, measured.** A real run's profiling step closed at `+33h2m`, and answering *why* meant reading
file birth times against modification times from outside the run: one number per agent, dispatch to
last write, with no way to see which of its six steps spent the time. The file holds ten lines saying
what each step was and not one saying when. A profiler that fetches a pricing page, SimilarWeb and a
funding search in eleven minutes is a different problem depending on which of the three took nine of
them, and the log cannot say.

**The change is one line of `runlog.mjs`** — `beat` writes `${stamp(at)}  ${text}` the way `note`
already does. Nothing else moves:

- **The stuck-agent check is unaffected.** Its trigger stays the modification time, which is still
  the only thing that says *how long ago* rather than *when*. What it gains is a second question it
  can now answer once it has looked: not just that an agent has been quiet for eight minutes, but
  that the step before this one took nine.
- **The dispatch template already carries the command**, and its *"do not stamp it with a time"*
  stays true — it becomes *do not stamp it yourself*, for the reason every other timestamp in the run
  has: you have no clock, and a composed stamp is wrong silently.
- **No agent's *Logs* row changes.** Those rows say what an agent announces, not how the file is
  formatted, and eleven copies of the format is the duplication `AGENTS.md` exists to prevent. The
  format is stated where the line is written and where the file is read.

**And it is the second time this file has recorded the same lesson**: the run log exists because *"the
timestamp comes from the shell, never from the model"*, and the heartbeat is the one place a line went
in without one.

### Every temp file carries the agent's label, and the rule has to reach the agent — TO BUILD

Applies to every agent here, for the same reason the check above does.

**Observed twice in real runs, on two different agents.** Two Page Analysts wrote to the same scratch
file and overwrote each other. Then two **Source Analysts** ran concurrently and both wrote
`scratchpad/observations.md`; the websearch agent's write clobbered the hackernews agent's mid-run.

**Nothing was lost either time, and that is the least reassuring part of it.** On the second, the
Hacker News raw report had already been built from the correct text, and its analyst patched the
observations back into the JSON and verified them as Hacker News content — then checked the websearch
report for the reverse contamination, which was clean. It survived because an agent happened to
notice. **The failure mode it survived is one source's observations ending up inside another source's
report**, and a scratch file has no reader to complain, so nothing else in the run would have caught
it.

**Two things are wrong, and only one of them is the filename.**

**The filename has no label.** `phases/index.md` names the *directory* a temp file goes in and stops
there, so two agents working at the same time land on whatever name each invents — and identical
prompts invent identical names. `observations.md` is exactly the name both Source Analysts would
reach for. **The filename carries the dispatch's `<label>`**, the one its `_returns/` and `_progress/`
files already use; for a Source Analyst that is its source, which is precisely the collision. One
writer per file is `AGENTS.md`'s rule, and a shared scratch file breaks it as surely as a shared
output would.

**The rule lives where no sub-agent can read it — and that is the root cause.** It is in
`phases/index.md`, which **is never sent to a sub-agent**: `brain/index.md` §Sub-agents says an agent
is sent its own file and its source file *"and nothing else — the files are self-contained on
purpose."* So every agent that writes scratch has been inventing both the path and the name with no
rule in front of it, which is why one landed in `scratchpad/` — outside `digmore/<slug>/` altogether,
breaking the harder half of the rule that nothing a run produces lands outside the topic subtree.

**This exact failure has already been diagnosed once in this file**, for the heartbeat and the
`output.md` lines: both lived in a block only agents returning a shape received, so an agent that
wrote prose or edited a file in place silently got neither. The fix then was to move them into every
dispatch. **The scratch-file rule takes the same route and for the same reason** — it belongs in
`dispatch_structured_subagent.md` §"Every dispatch carries this", which is the only text every agent
is guaranteed to see.

**Where each half lands:**

- `dispatch_structured_subagent.md` — the rule itself, in the block every dispatch carries: where a
  temp file goes, and that its name carries the label the dispatch was given.
- `phases/index.md` — the filename requirement beside the directory it already names, so the two
  halves of the rule sit together for the orchestrator.

### The orchestrator's own writes have no rules — TO BUILD

**Two failures in one step of a real run**, both in the Record step of Audit, where the orchestrator
appends the Run footer to the summary. Every rule about writing that the run has was written for
sub-agents; the orchestrator writes `research_plan.json`, `players.csv`, the enriched cells and the
footer, and nothing says how. (`audit.md` and the verdicts were on this list until §"`audit.md` is
appended as the run goes" and §"Vet's context is the input, not the return" moved both to scripts —
which narrows what this rule covers without touching why it is needed.)

**1. It wrote scratch to `/tmp`.** The rule that a run's temp files live under
`digmore/<slug>/cache/_misc/` is in `phases/index.md` §"Where a run writes" — read once, at the start
of a run, and 30-odd hours behind it by the time Audit needs a scratch file. **Sub-agents already
have this fixed**: the same rule was moved into the dispatch template because it was not reaching
them (§"Every temp file carries the agent's label", above). The orchestrator was never given the same
treatment, and it is the actor furthest in context from where the rule is written.

**Windows is the only reason it was seen.** Node resolved `/tmp` to `C:\tmp` and the read failed, so
the run noticed and moved the file inside the topic. On macOS it would have written there silently,
and run material would have sat outside the topic subtree with nothing reporting it.

**So the rule goes where the orchestrator writes scratch**, in the phase files that do it — Synthesize
and Audit — rather than only in the cross-phase file it read at the start. Same fix as the
sub-agents', at the orchestrator's own address.

**2. It executed part of the footer instead of writing it.** The append used an unquoted heredoc, so
the shell ran the backticked filenames in the text as commands:

```
/usr/bin/bash: line 12: audit.md: command not found
/usr/bin/bash: line 12: extract.fetchesPerBranch: command not found
```

It retried with `<<'FOOTER'`, checked `verify backticks intact`, and nothing was lost. **What makes it
worth a rule is what it was one quote away from**: a 145 KB deliverable, silently altered, with the
run reporting success. The footer is full of backticked filenames and the summary is full of `$` and
backticks, so this is the ordinary case rather than an unlucky one.

**Nothing in the skill says how the orchestrator gets text into a file.** `modes.md` says scripts run
through Bash; the footer is not a script. With no mechanism named it improvised `node -e` with the
document inline, then a shell heredoc — two parsers deep on text written to be read, not executed.

**The rule, and it is about text crossing a parser rather than about which tool is nicer:**

- **Changing an existing file → the edit tool.** Only the changed region crosses, and no shell reads
  the content. It is also the cheapest of the three for a large document.
- **A heredoc, where one is used, always quotes its delimiter** — `<<'EOF'`. That quote is the whole
  difference between the footer being written and being run.
- **Never `node -e` with document text inline.** Shell, then JavaScript, both parsing prose.

**Writing the whole file back is the expensive option, not the safe one** — the summary is 145 KB and
the harness reads a file before overwriting it, so a full rewrite pays for it twice. Recorded because
"use the file tool" is the obvious-sounding rule and it is the wrong one here.

**The temp-file-then-rename rule is untouched.** The summary is still written as `.tmp` and renamed
over the original; the rename is a shell command either way. What changes is that the document's text
no longer passes through the shell to get there.

### The dispatch template closes, and two agents return `done` — DECIDED

Applies to every agent here, like the two checks above.

**The gap.** `dispatch_structured_subagent.md` says *"then return what you found"* and *"Return
exactly this JSON, and write the same JSON to …"*. Both say **what** to return and neither says
**only** that, and prose walks through the opening: all 85 sampled Page Analyst returns carried text
outside the JSON, ~540 tokens each.

**Add the missing sentence for every agent: nothing outside the JSON.** No greeting, no summary, no
account of the work. That is the whole edit to the shared template, and it applies to all of them.

**`done` is a per-agent override, not the new default.** #2 and #3 state it in their own entries,
because they are the two dispatched hundreds of times per run and the two whose product is already
wholly on disk. **#1, #6 and #11 keep returning their shape this round** — each runs a handful of
times, and what each hands back is read directly rather than looked up.

**One trap in this edit, and it is why the template's own test changes.** The second block — the one
sent to agents "whose return has a shape" — is where the schema is pasted in full and where the
`cache/_returns/<label>.json` path is given. **It is the only place an agent learns what to write and
where.** Make #2 and #3 return `done` and they stop qualifying by that wording, so the block that
makes a `done` return possible would be withheld from precisely the two agents that return `done`,
leaving them told to write a file with no shape and no path.

**So the test becomes whether a shape comes out of the dispatch at all — returned, written, or
both — never which route it takes out.** "Returns a shape" drops #2 and #3 the moment they return
`done`. "Writes a shape" would have dropped #5, which returned its verdicts and wrote no file —
though #5 now writes one per handle, so as it happens every agent currently writes. **State it by
route-independence anyway**, or the next agent that returns without writing falls through the same
gap. It is the same correction this file
already made once, when those two lines were moved out of the shape-only block for agents returning
prose.

### What a dispatch costs your context, and the two things it stops pasting — TO BUILD

**DECIDED.** Peter, on why this matters: *"I want to save on the context of the main orchestrator —
if it duplicates text across sub-agents, text that also appears in the sub-agents' md files, this is
waste."*

**Every word of a dispatch is composed by the orchestrator and stays in its transcript for the rest
of the run.** A sub-agent's context dies when it returns; yours has to survive six phases. So the
prompt is not free the way the agent's own reading is free — a path costs the agent one read and
costs you nothing, while a pasted paragraph costs you it once per dispatch, ~150 times in a run.
This is the same asymmetry that put the bulk material on disk; the prompt is the part of it nobody
had measured.

**Two things stop being pasted. One rule stops the rest coming back.**

**1. The agent prints its own shape.** The template tells you to run `validate.mjs --shape <name>`
and paste the whole entry into the prompt. The agent can run that command itself, and the dispatch
names the shape instead of carrying it — the same one entry, the same `description`, and none of it
in your transcript.

**What the saving actually is.** It is spread across the repeated dispatches rather than concentrated
in the biggest shapes: `page-analyst` around 108 times once its URLs are batched, `player-profile`
~47, `handle-vetting` ~40, `claim-fact-checker` ~30, `branch-searcher` 27. That is roughly 250
dispatches carrying 300 to 500 tokens of schema each. **`source-raw-report` is not one of them** — it
is one dispatch per source, at most a dozen in a run, and an earlier draft of this section had it at
"hundreds", which overstated the case by an order of magnitude on that shape.

**Why this one is safe when the standing block is not.** A pasted rule that an agent skips fails
silently — no heartbeat file, a scratch file at a name another agent also picks, prose in the
return. **The shape is the one pasted thing whose omission is caught**: every return and every

### The run log — NEW

**DECIDED — the orchestrator writes one log for the whole run, at the topic root.** Peter: *a main

### What counts, and what is judgement

**Mechanical, in the script — the floor.** A player is a candidate at **5+ documents across all
sources**, counted after the claim filter. One document that names a player counts once, however
many times the name appears in it.

| Handle verdict | Claims reach the report | Count toward the 5+ |
|---|---|---|
| `legit` | yes | yes |
| `unknown` | yes, caveated | yes |
| **`unvetted`** — no verdict exists: below `vet.handleCapPerSource`, or first seen in expert material after Vet finished | yes, caveated | yes |
| `promoter` | yes, labelled as a promotional signal | **no** |
| `spammer`, `throwaway` | no | no |
| **no handle at all** — websearch, local | yes, filtered on `pageQuality` | yes |

- **Claims with no handle count.** They are most of what is said about a company — vendor pages,

  them a company would be judged on forum chatter.

### The batch — DECIDED

**One dispatch reads up to `extract.urlsPerDispatch` URLs instead of one.** Peter. Nothing about the
per-document work changes: one document still produces one stripped page and one claims file, the
claims still never enter the orchestrator's context, and the pagination, the stripping and the claim
extraction are the same on every URL. What changes is how many agents that takes.

**Why — the dispatch itself is the cost, and it is charged whatever the agent says.** Launching a
sub-agent and taking its completion back spends roughly 370 tokens of harness scaffolding in the
orchestrator's context, before a word of the agent's own answer. Extract dispatches this agent up to
~700 times, so the run pays about 140k tokens for the scaffolding alone — in the one context that has
to survive all six phases. **Everything else has already been moved out.** The claims went to disk,
the extraction became a receipt, and the receipt became the word `done`; the scaffolding is what is
left, and it cannot be shortened. Batching is the only instrument that touches it, and it divides the
bill by `extract.urlsPerDispatch`.

**The batch is one branch's, never a mix.** Each URL has exactly one owning branch by the time this
agent is dispatched — the dedupe in `extract_phase_b.md` keeps the highest-relevance copy and charges
its fetch to the branch that copy ranked highest in — and the orchestrator totals `pagesRead` per
branch to enforce `extract.fetchesPerBranch`. A batch spanning two branches would return one array
with the fetches of both in it, and the tally that enforces the cap would be a guess. **The last batch
of a branch is whatever the branch has left**, which is how a `fetchesPerBranch` that does not divide
evenly still lands exactly on its cap.

**One branch is the tighter of two bounds, and it subsumes the looser one: one source.** A branch is
one angle paired with one source, so a single-branch batch is a single-source batch by construction —
but not the reverse, and the difference is not cosmetic. Two URLs off the same source through
different angles are two branches with two separate budgets, and batching them together breaks the
tally exactly as a cross-source batch would.

**Cross-source is not merely inaccurate, it is undispatchable.** The source decides which
`<source>.md` this agent is sent and which tool it reaches for, and it is sent one file — so a batch
holding a Reddit thread and a forum page is a batch where the agent has instructions for one of them
and is guessing at the other. That is why the source arrives as one word for the whole batch rather
than per URL: a per-URL source field would make the impossible case expressible, and the shape should
not be able to say it.

The same holds in Enrichment, where an expert *is* a branch and `enrich.urlsPerExpert` is its budget:
a batch is one expert's URLs.

#### A branch's batches go out in waves — DECIDED

**One batch at a time per branch: dispatch it, read its receipts, add its `pagesRead` to the branch's
tally, then send the next — until the branch's budget is spent or its URLs run out.** Peter.

**This is what makes `extract.fetchesPerBranch` a cap again**, and it was not one before. The
orchestrator keeps the branch's top `fetchesPerBranch` candidates and used to dispatch every one of
them at once — but **pages are fetches**, so twenty URLs each paginating to
`extract.maxPagesPerDocument` spend five times the budget, and the receipts that would have stopped it
arrive after the spending. `extract_phase_b.md` calls it *"a hard cap, not advisory"* and describes *"a
branch that spends all 20 on one long thread"*, which is the behaviour it wants and could not reach.
A wave is a decision point between dispatches, and the tally is only actionable at one.

**It cost too much before batching and does not now.** Waves over one URL each would have serialised a
branch into twenty round trips; over batches it is a handful, and the dispatches saved pay for them.
The overshoot that remains is bounded by one batch —
`extract.urlsPerDispatch × extract.maxPagesPerDocument` in the worst case, where every document in the
last wave paginates to its limit — and that is worth writing down rather than discovering.

**Branches still run in parallel, and there is no barrier between them.** The wave is inside a branch
and nowhere else: every branch starts its first batch at once, and each moves to its next wave the
moment its own returns, never waiting on another branch's. A branch that fills its budget in wave one
stops there while the rest carry on. **A cross-branch barrier would be the expensive mistake here** —
it would hold every branch at the pace of the slowest, which is the open web every time.

**Peak fan-out becomes one agent per branch rather than one per URL**, which is the second saving and
an unplanned one: the concurrency limit that `extract_phase_b.md` has a whole throttling procedure for
is far less likely to be reached at all.

**Nothing re-orders the URLs into waves — DECIDED.** Peter: *I don't trust this relevance and we don't
need to add an extra complexity of ordering based on it.* They go out in the order the dedupe left
them in. `relevance` exists on every candidate and the dedupe already reads it to pick between copies,
but it is one searcher's judgement off a search snippet rather than a measurement, and sorting waves by
it would spend real complexity on a number we do not believe.

**The cost, stated rather than discovered: a branch whose budget fills in an early wave read whichever
URLs came first, not the best ones it found.** That was already true of the fetch cap — it keeps the
top `fetchesPerBranch` candidates and any of them may eat the budget by paginating — so waves change
which URLs go unread, not whether some do. What both leave behind is recorded the same way, in
`audit.md` under "dropped-for-budget".

**Sequential, never dispatched — and this is the carve-out from the rule against batches.**
`phases/index.md` says a sub-agent is *one item, because a batch invites a fan-out*: "fetch these 12
URLs and extract from all 12" is a compound job over independent items, it reads as an invitation to
parallelise, and a sub-agent that dispatches work cannot await it, so it hangs. **That reason applies
here in full** — there is fetching to fan out, which is exactly what #11's identical carve-out did not
have to contend with. So the prohibition is carried in words rather than in the shape of the job, and
the dispatch says, verbatim:

```
Fetch these one at a time, in the order given. Finish each URL completely — fetch it,
paginate it, strip it, write its page and its claims — before you start the next one.
Do not dispatch sub-agents. Do not parallelise. You receive no completion notification
for anything you start, so whatever you start you wait on forever.
```

It is still one verb over one kind of item; what it is no longer is one item. Sequential is not a
performance preference — an agent that fans out here hangs, and the batch is lost rather than slow.

**`extract.maxPagesPerDocument` still bounds each document individually.** It is not divided across
the batch and it is not a batch total: five URLs is five documents, each followed to its own limit. It
stays the one configuration this agent enforces itself, for the reason it always did — it bounds the
thing the agent can see.

### Vet's context is the input, not the return — DECIDED

**The problem, in what the run does today.** Peter, on finding it. The orchestrator reads every handle
row twice — once to pick who gets vetted, once to copy each row into that handle's dispatch prompt —
up to `vet.handleCapPerSource` handles per source, on four sources.

**And a row is not just a name**: it carries `pageSignals`, everything the pages already showed about
the person, and `documents`, a list of every cached file they appear in. Two hundred of those are far
more than the verdicts coming back, which are a verdict, a relevance and one sentence each.

**After this change the orchestrator never reads a handle row at all.** It asks a script how many
handles a source has left, dispatches ranges against that count, and the agents read their own rows.

**The dispatch carries a range, and nothing else about the handles.** *"Handles 11–20"*, the source,
and the research question. The agent asks a script for its own handles. **The orchestrator holds a
count and a range per dispatch and never learns a handle's name** — which also removes the transcribe
step that put 26 wrong-typed rows into `<source>-handles.json`.

**One file per handle, written by the agent that judged it.** `cache/<source>/handles/<handle>.json`,
written as each handle finishes. The file existing means that handle has been vetted, which is the
resume check for free. **This is what keeps the one-writer rule** — `AGENTS.md` says a fan-out writing
to one shared file *"is a design to change, not a design to add a lock to"*, and a per-handle file has
no contention to lock against.

**Why `cache/` and not beside the output.** Considered and decided the other way round from #3's: the
per-handle file is superseded the moment it is merged, and a cleared cache costs a re-vet the script
cache mostly pays for anyway. The conclusions live in `<source>-handles.json`, which is not in
`cache/`.

#### `handle_vetting.mjs` — new script, three calls

**Call one — prepare, once per source, before any dispatch.** In order:

1. Read the ranked `<source>-handles.json`, take the top `vet.handleCapPerSource`.
2. Match each handle against `experts.csv` by its platform column, reusing `experts.mjs`'s matching
   rather than a second copy of it.
3. **Write the matches straight into `<source>-handles.json`** as `verdict: legit` with what the CSV
   holds, `verdictReason` naming `experts.csv`, `vettingSignals` empty.
4. Drop from the remainder: the auto-promoted, anything already carrying a verdict, anything already
   having a file in `cache/<source>/handles/`.
5. Decide Twitter's depth over what is left — top `twitter.handlesDeepVetted` get
   `--posts <postsPerDeepVet>`, the rest `0`.
6. Write the remainder to `cache/<source>/vetting-worklist.json` and return the count.

**Step 2 is the branched-topic case, and it is the only thing `experts.csv` is still read for during
Vet.** A child inherits the parent's file *by copy at the moment of branching*, so those people appear
in a handles file written fresh by this run's Source Analyst, with no verdict on them. Nothing else in
the file says they are already known.

**`vet_phase_c.md` step 2's other half goes.** It reads *"inherited from a parent topic **or written
earlier in this run**"* — and `experts.csv` is now written once at the end of Vet, so nothing is added
mid-run. That case is covered better anyway: the script already excludes anything with a verdict or a
handle file, without consulting `experts.csv` at all.

**Step 6 is what makes ranges safe.** Recompute the unvetted list on every request and it shrinks as
handles are vetted — so once the first batch finishes, *"handles 11–20"* addresses what used to be
21–30, and the original ten are never vetted at all. The frozen file is also the baseline the gap
report is measured against, so it is not overhead added for the ranges.

**Call two — serve a range**, once per vetter: the handles at those positions, with everything a
vetter needs, including that handle's own `--posts`.

**Call three — aggregate**, once per source, after its vetters have all stopped. Reads
`cache/<source>/handles/*.json`, validates each, discards the malformed, and merges the rest into
`<source>-handles.json` by joining on `handle`. **Never rebuilds that file** — the roster, the ranking
and the `documents` lists are the Source Analyst's and predate Vet. Then reports the gap: work-list
handles with no file, and anything discarded. **The auto-promoted were never on the work list**, so
they cannot read as missing.

**"All stopped" is not "all succeeded."** A vetter that returns a failure, or one the stuck-agent
check kills, is finished — it just produced no file. Waiting on success would let one dead agent hold
a source open indefinitely.

#### Where the write goes, and what it is not

**`<source>-handles.json` gains a fourth writer**, and it is this script, at two moments inside Vet:
the auto-promotions before dispatch, and the merge after. Still one writer at a time, so the rule
holds, but `phases/index.md`'s row has to say both.

**`experts.mjs` gains a verb, run once after every source is vetted.** It reads the merged handles
files, takes the `legit`-and-on-topic rows, and folds each through the existing `merge`, so
`rowMatches`, the union rules and the `POSSIBLE DUP` flag behave exactly as they do today. One bad row
is recorded and skipped rather than aborting the rest — which is what cost 48 verdicts in a real run,
when `experts.mjs add` threw on the second handle of a loop and the handles write came after it.

**Running it once is not a regression on the incremental-write rule.** That rule exists because *"a
run that stops at handle 30 would otherwise reach no write at all, and thirty dispatches would be
gone."* The per-handle file satisfies it earlier and better: it survives the orchestrator dying, which
the orchestrator's own write cannot.

**It cannot run per source.** Enrichment's expert step round-robins across sources to a single
`enrich.expertsFollowed` budget, and `players.mjs candidates` counts the five-document floor across
all sources — so Enrichment is globally coupled at two points and there is no early start to buy.

#### What the labelled identifiers change

**The vetter labels each identifier rather than returning a bag of strings.** `realName`, `github`,
`website`, the platform handles, plus `otherIdentifiers` for anything fitting no column. It is the
agent that read the profile and saw which was which; everything downstream sees three strings and
guesses with less information than the agent had.

**That is what lets a script write `experts.csv` at all.** The mapping from `statedIdentifiers` to
`github` / `website` / `real_name` is interpretation, and `experts.mjs` infers nothing — every column
arrives as a flag. Labelled at the source, the mapping becomes a copy.

**It also improves duplicate detection**, which matches on exact equality of `real_name` or a handle
column. A GitHub handle that lands in the wrong column, or nowhere, is a real person appearing twice.

#### Schema changes this needs

- **New `handle-vetting`** for the per-handle file, every field typed. The untyped return is what let

#### Filenames — `utils.mjs`

**Do not move `assertWorkspaceRoot` or `parseArgs` in the same change.** Four scripts import the first

### A script writes `claim_index.json`, not the agent — TO BUILD

**DECIDED**, off a real run. The Raw report writer stalled for 12 minutes on its last step: it emitted
`claim_index.json` as model output, hit the output limit part-way through, and restarted in batches.
Dozens of sequential write calls, no heartbeat between them — and the stuck-agent check kills at 10
minutes, so the run was one check away from killing a healthy agent mid-write of the file the whole
fact check reads.

**What is actually judgement, field by field:**

| Field | Who produces it |
|---|---|
| `citations[]` — `quote`, `url`, `cachedPage`, `handle`, `status` | a **copy** from `<source>-joined.json`, verbatim |
| `importance` | **max()** of the merged set |
| `pageQuality` | **max()** — the canonical citation's |
| `claimId` | a **counter** over the merged set |
| `claim` | **judgement** — one statement for the three that merged |
| `refutedBy`, `refutedReason` | **judgement** — which won, and one line why |

**The citations are the bulk of the file and every one is a copy.** A merged claim carries up to three,
each with a full verbatim quote, and the agent is retyping quotes it read minutes earlier. That is the
slow part, and it is also a correctness risk: the fact check compares the report against the cached
page, so a quote that drifts while being retyped sends it to the wrong evidence.

**The split.** The agent returns a **merge manifest** — per merged claim, the source claim references
it groups, the merged `claim` text, and `refutedBy`/`refutedReason` where it lost. A new
`synthesis.mjs index` verb reads that plus the six `<source>-joined.json` and writes the file:
resolving each reference, copying its citations, taking the two maxima, numbering the result.

**It is the same split `synthesis.mjs join` already made** — *"a join, a lookup and a filter give the
same answer every run, and an agent handed arithmetic drifts off it."* Merging is semantic and stays
the agent's; expanding the merge is not.

**What it saves.** The write side only — the read is the merge and does not move. The agent emits a
compact manifest instead of 47 KB of JSON, which is what removes the output-limit stall.

**Validation moves to the manifest, and gets stronger.** A script's output needs no runtime check
(§"Whoever writes a JSON validates it"), so `validate.mjs claim-index` leaves the agent. The manifest
is model output and is checked instead — a smaller payload, and the script can additionally fail on a
reference that does not resolve, which a shape check never could: it reads structure, not whether a
quote is real.

**One clause to reword, not a guarantee to replace.** The agent's file says the raw report and the
index cannot drift because one agent writes both from one merge. That still holds — both still come
out of one context and one merge — and the only change is that the index is expanded from the
manifest by a script rather than typed out.

  **A refuted claim is in the report, so it is checked like any other — DECIDED.** #7 sends the loser
