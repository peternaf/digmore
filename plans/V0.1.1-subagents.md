# digmore V0.1.1 — sub-agent definitions

Baseline: the skill as built at commit `da94c5a`, read 2026-08-19.

Marks: **(spec)** a stated cap · **(arithmetic)** caps multiplied, no total is stated ·
**[TBD]** the skill does not say · **[OPEN]** identified, not decided · **WRONG** the skill
contradicts itself · **MISSING** a capability nothing provides · **[DRAFT]** written from what the
skill does today, for Peter to replace. Each carries a `> **Peter:**` line to fill in.

**Purpose** is the first field on every agent: the one job it exists to do, in a sentence. Not when
it runs (**Phase**) and not what one dispatch covers (**One dispatch per**) — why it is a separate
agent at all. Every one is **[DRAFT]** today.

"Sent" means the path is written into the agent's prompt and it opens the file itself.

**This file is the source of truth.** Where it and a skill file disagree, this file wins and the
skill file is what changes. A **WRONG** row is not a question — it is a skill file that has not
caught up yet.

**The orchestrator** is the fourteenth actor in this document and the only one that is not a
sub-agent: the main session, running the skill from the first phase to the last. It is a worker, not
a wrapper. It talks to the user — the only actor that can — decides the plan, dispatches every agent
below and waits on them, checks what comes back and repairs or drops it, counts the budgets, and
writes every file no single agent owns: `research_plan.json`, `audit.md`, `experts.csv`, the verdicts
in `<source>-handles.json`, the enriched cells in `players.csv`.

It is also the one context that has to survive all five phases, while a sub-agent's dies the moment
it returns. That asymmetry is why the bulk material goes to disk and only receipts come back.

## 1. Scoping agent

- **Purpose:** **[DRAFT]** Find out what the subject actually is before the run commits to searching
  it — the words its own people use, the names that keep coming up — and turn that into the angles
  every later search is built on.

  > **Peter:** Its findings direct the rest of the run — both what gets researched and how the
  > output is presented. It settles the angles and the vocabulary; the orchestrator then decides the
  > deliverables and sections from them, using the command's reference file and, in manual mode, me.
  > Two steps, and this agent is the first one.
- **Phase:** Plan
- **One dispatch per:** the topic
- **Full run:** 1 (spec)
- **`--fast`:** 1 — 2 angles instead of 3–6, and less looking behind them
- **Input**
  - *Task text:* the topic as the user phrased it, the mode's angle count, and the job — find out
    what this subject actually is (the vocabulary its own people use, the names that recur), then
    decompose it into the angles the run will search. Explicitly not the sections; those need the
    command's reference file and the user, and it has neither.
  - *Rule files sent:* `brain/subagents/scoping_agent.md` — its own file, the whole job.

- **Returns to main context:** JSON `scope` — the vocabulary the subject's own people use, the
  names that recur, and 3–6 angles (2 in `--fast`), each with a kebab-case label, a search-ready
  query and a rationale.
- **Writes to disk:** nothing it fetched — what it read on the open web is not kept.
  `digmore/<slug>/cache/_returns/scoping-agent.json` — a copy of what it returned, on disk

- **Log file:** `digmore/<slug>/cache/_progress/scoping-agent.log` — one line before each step:
  - `searching <query>` — one per WebSearch call, and there is no cap on how many it makes
- **Size per dispatch:** large — reads a lot of the open web to hand back a little.
- **Dispatch site:** `plan_phase_a.md:23`
- **Concurrency:** n/a — single
- **Missing rules:** none.
- **Not its job, deliberately:** the summary's sections. `plan_phase_a.md` §3 keeps

  reference file and, in manual mode, the user.

## 2. Branch Searcher

- **Purpose:** **[DRAFT]** Find what is worth reading for one angle on one source, rank it, and hand
  back the list with a relevance score per URL — that ranking is what decides which pages the run
  spends its budget on. Discovery only: it does not open the URLs or posts it finds. Judging the
  content is the Page Analyst's job; judging the *candidates* is this one's.

  > **Peter:**
- **Phase:** Extract
- **One dispatch per:** one branch — one angle paired with one source
- **Full run:** 18–36 (arithmetic: 3–6 angles × up to 6 sources)
- **`--fast`:** ~12 (2 angles × sources)
- **Input**
  - *Task text:* one angle `{label, query, rationale}`, one source name, the topic slug, the
    branch's fetch budget.
  - *Rule files sent:* `brain/subagents/branch_searcher_agent/index.md` and that agent's
    `<source>.md` — both named in the job text, per `extract_phase_b.md:29`.
    `brain/output.md` — always.
  - *Data files sent:* none — this agent is the one creating material.
- **Runs:** `api.mjs reddit search` **twice** on Reddit — site-wide, then scoped to subs it picks
  itself · WebSearch with a `site:` filter on HN, Twitter and forums · plain WebSearch on the web
  source · on local, copies the user's named files into `cache/local/`.
- **Returns to main context:** JSON `branch-searcher` — `results[]` of `{url, title, relevance}`.
  **CLOSED — no `maxItems`, and that is fine.** The volume is already bounded upstream: the branch
  count is angles × sources, at most 36, and each branch runs one search. Whatever one search yields
  is what comes back, and if that is 200 candidates the orchestrator dedupes them and cuts to
  `fetchesPerBranch` before anything is read. Capping the *return* would only hide candidates the
  ranking might have wanted.
- **Writes to disk:** search responses only — never a page, a thread or a post.
  - **Reddit** — `digmore/<slug>/cache/reddit/reddit-search-<subs|sitewide>-<sort>-<window>-<qhash>.json`,
    written by the script.
  - **Hacker News, Twitter, websearch, forums** — nothing. WebSearch results live in what it
    returns.
  - **Local** — the user's named files, copied into `digmore/<slug>/cache/local/` under their
    original names. The one place this agent writes something other than a search response.

  `digmore/<slug>/cache/_returns/branch-searcher-<angle>-<source>.json` — a copy of what it returned.
- **Log file:** `digmore/<slug>/cache/_progress/branch-searcher-<angle>-<source>.log` — one line
  before each step:
  - `searching <source> for <query>`
  - `copying <filename>` — local only, one per file the user named
- **Size per dispatch:** small — one search and a URL list, on every source. It fetches nothing.
- **Dispatch site:** `extract_phase_b.md:11`
- **Concurrency:** all at once, capped only by the harness limit preflight reported
  (`extract_phase_b.md:13`).
- **Missing rules:** none. **Recency is settled and built** — the scripts apply the window because
  they can do it properly (Reddit `--after-date`, Hacker News `numericFilters`, Twitter by reading
  `created_at` off each tweet after the fetch). WebSearch's `after:` is not used: it is approximate
  on the open web, and on x.com it actively suppresses organic results in favour of indexed
  marketing accounts. In `branch_searcher_agent/index.md`.

  > **Peter:** The recency shuldn't apply to regular webserarch, it should apply to our other special searchers
- **Missing functionality**
  - **DECIDED — the orchestrator dedupes the URLs.** It has every branch's results in context, so
    it cuts duplicates before dispatching readers. Nothing changes in this agent. Still to write
    into `extract_phase_b.md`.

    > **Peter:** the orchestrator should check all the urls and dedup - anyway it has all the urls in context.

  - **DECIDED — on Reddit it searches twice: site-wide first, then subs it picks itself.** Built, in
    `branch_searcher_agent/reddit.md` §"Two searches, in this order".

    The file used to say multi-sub was the default and site-wide "returns too much off-topic noise" —
    but nothing anywhere told this agent *which* subs to pass. The Scoping agent returns vocabulary,
    recurring names and angles, and `research_plan.json.scope` carries no sub list. So a Reddit branch
    picked subs on its own judgement and had no way to tell a bad pick from a quiet topic: a wrong or
    non-existent `--subreddit` comes back near-empty **and does not error**.

    The picking is right and stays. What was missing is the pass that makes it readable.

    So: **site-wide first**, which cannot miss a community nobody thought of and whose hits show where
    the topic is actually discussed; then **scoped**, on the subs the site-wide hits clustered in
    **plus any this agent judges relevant whether or not they surfaced** — site-wide ranking favours
    large general subs, so a small specialist one can be exactly right and never appear. Both searches
    merged and deduped on URL into one return.

    It also makes a thin result readable: site-wide full and scoped thin means the subs were wrong;
    both thin means Reddit is thin on the topic, and only then may the run say so.

    Two API calls per Reddit branch instead of one, and two cache files — the site-wide pass names
    itself `sitewide`, the scoped pass names itself after the first sub, so they never collide.
    Neither counts against `fetchesPerBranch`: that cap bounds pages fetched, and this agent fetches
    nothing.

    > **Peter:** the branch searcher should start from sitewide search and also add to it sub reddit that it itself thinks could be relevant (not necessarily related directly to sitewide search)

  - **CLOSED — no discard count.** A branch that found 200 and kept 20 reads the same as one that
    found 20, and that is accepted.

    > **Peter:** this is fine, no need to change.

- **Peter's guidelines** — anything about this agent as a whole:

  >THIS SUBGAENT DOES NOT SAVE THREAD RESULTS, OR PAGES, OR ANYTHING THAT IS A SINGULAR ONLINE PIECE OF KNOWLEDGE. THIS STEP -ONLY- SAVES SEARCH RESULTS. 
  > The cache file name of this subagent doesn't make sense. there is a subagent instance per branch, but the cache file is for source? let's discuss this

     **Branch identity is already kept — in two other files.** Every dispatch writes
     `_returns/branch-searcher-<angle>-<source>.json` and
     `_progress/branch-searcher-<angle>-<source>.log`, both named for the branch. Those are where
     "which branch found what" lives, and they stay.

     The cache file is deliberately not one of them. It is keyed on the *request* — query, subs, sort,
     window — because that is what makes it a cache: two branches that issue the same query on the
     same subs should hit one file rather than pay twice. Putting the branch in that name would give
     every branch its own copy and the cache would stop working.

     **DECIDED — keyed on the request, no hash. The name is readable:**

     ```
     reddit-search-<scope>-<query-in-4-words>.json
     ```

     - **`<scope>`** — the first `--subreddit` in the order given, lowercased, non-alphanumerics to
       `-`. `sitewide` when none was passed.
     - **`<query-in-4-words>`** — the query reduced to its first four meaningful words: lowercase,
       punctuation to spaces, stopwords dropped (`a the of for in on to and or is are what how why do
       does vs`), first four of what remains, joined with `-`.

     **`api.mjs` derives it, not the agent.** A cache key has to be a pure function of the request —
     if two agents summarised the same query in their own words the file would never be hit twice.

     Worked example — `--subreddit LocalLLaMA --subreddit selfhosted`, query
     `what are the vram requirements for local llm inference`:

     ```
     reddit-search-localllama-vram-requirements-local-llm.json
     ```

     **Collisions are handled by the file, not the name.** Four words cannot carry the extra subs, the
     sort, the window or the rest of the query, so two different requests can land on one name. Without
     a check the second search opens the first one's file and reports another query's results as its
     own — no error, just a wrong answer that looks normal.

     So the script writes the full request into the cached JSON and compares it on read: open
     `<name>.json`, and if the stored request matches, that is a hit. If it does not, try
     `<name>-2.json`, then `-3`, until either a match or a free slot, which it writes. **The match is
     on the stored request, never on the number** — so a re-run finds its own file whichever number it
     landed on first, and order decides which number, never which data. With no collision it is one
     file and one comparison.

     Changes `api.mjs` (`cacheKey`, plus the stored request and the read comparison) and the
     cache-layout section of `branch_searcher_agent/reddit.md`. The 60-character collapse rule goes —
     it existed only because the old name joined every subreddit into itself. Old files miss and
     re-fetch once.

## 3. Page Analyst

- **Purpose:** **[DRAFT]** Turn one page into evidence: fetch it, strip it to readable text that
  keeps its structure, and pull out the checkable claims with the words the source used.

  > **Peter:**
- **Phase:** Extract
- **One dispatch per:** url or post from hackernews, or reddit or twitter. a single piece of online data to get and analyze.
- **Full run:** up to ~700 (arithmetic: 36 branches × `fetchesPerBranch` 20)
- **`--fast`:** up to ~60 (12 branches × 5)
- **Input**
  - *Task text:* one URL and **which of the six sources it belongs to** — reddit, hackernews,
    twitter, websearch, forums or local. That word is not a lookup this agent performs; the
    orchestrator already knows it, because the URL came back from a branch and a branch is one angle
    paired with one source. It decides two things before any work starts: which `<source>.md` this
    agent is sent, and which tool it reaches for.

    Plus the branch label, so the log line and the fetch tally can be attributed.

    **No fetch budget is passed.** It was in this line and it is gone: the cap is `fetchesPerBranch`,
    it is per branch, and one agent holding one URL cannot see the other nineteen — a number it
    cannot act on is a number it will misread. The orchestrator counts fetches from the `pagesRead`
    on each receipt and stops dispatching when the branch is full. The only ceiling this agent
    enforces itself is `extract.maxPagesPerDocument`, which bounds one document, which it can see.

    The claim shape is no longer passed as task text either — it is `page-claims`, written out field
    by field in this agent's own `index.md` §"Read it — the claims", which it is sent anyway.
  - *Rule files sent:* `brain/subagents/page_analyst_agent/index.md` and that agent's `<source>.md`.
    `brain/output.md` — always.
  - *Data files sent:* none, and that is right. Everything it needs it fetches; the one thing it
    might have been handed — the page — is the thing it exists to go and get. The rules it needs that
    are not in its own two files (`page_quality.md`'s values) belong in the rule-files
    line, not here.
- **Runs:** one script per source — `api.mjs reddit thread <id>`, `hackernews.mjs story <N>`,
  `api.mjs twitter tweet <id>`, or `fetch.mjs <url> --output-dir digmore/<slug>/cache/<source>` on
  websearch and forums, which names the file itself and returns a page already on disk without a
  request. On a bot wall, WebFetch instead, saved under the `filename_only` the failed call carried.

  **Paginate first, parse second.** On websearch and forums it follows the document to its end —
  every page a fetch, bounded by `extract.maxPagesPerDocument` — and only once it has them all does
  it merge them into one markdown file, strip it, and read the claims out of it. The three scripted
  sources return the whole thing in one call and have nothing to paginate.
- **Returns to main context:** **DECIDED — a receipt, not the claims.** JSON `page-analyst`, and it is
  four fields: `outcome` (`ok` / `blocked` / `nothing-found`), `claimCount`, `pagesRead`,
  `fetchedWith` — whether the page yielded anything, how much, what it cost the branch's budget, and
  which tool got it. The last two feed `audit.md`: blocked URLs, and URLs WebFetch had to shorten. Nothing else, not even
  the file's path: the claims go to `<name>-claims.json` in `cache/<source>/`, and the Source
  Analyst, the Report Writer and the Claim Fact Checker find them by reading the directory. This used to
  return `claims[]` with no `maxItems`, which across ~700 dispatches was the largest thing entering
  the main context; that is what the split removes. Every claim now also carries the `handle` that
  said it — the only link between a claim and a person anywhere in the run, and what #4 writes into `<source>-handles.json`
  ranks on.
- **Writes to disk:** `digmore/<slug>/cache/<source>/` — **two files per URL, sharing one filename.**
  Per URL, not per page: a document spread over eight pages is one pair, not eight.
  - *The page.* One markdown file, the whole document. On **websearch and forums** this agent
    paginates first — every page up to the limit — then merges them all into one file and strips it:
    readable content only, wrapping removed, headings, lists, tables, code blocks, authors and
    comment nesting kept. The raw pages `fetch.mjs` wrote are deleted once merged. On **reddit,
    hackernews and twitter** there is nothing to strip or merge: the script already wrote structured
    JSON (`reddit-thread-<id>.json`, `hackernews-item-<N>.json`, `twitter-tweet-<id>.json`) and that
    is the stored page.
  - *The claims.* What this agent extracted from that document, each claim with its verbatim quote —
    written to `<name>-claims.json` in the `page-claims` shape, and each one now carrying the
    `handle` that said it. These no longer come back with the agent — the return is a receipt.
  - **The filename comes from the URL**, derived by `fetch.mjs` — see the DECIDED item below. The
    scripted sources name themselves; for those, use the filename the script returned.
- **Log file:** `digmore/<slug>/cache/_progress/document-analyst-<source>-<n>.log` — one line before
  each step:
  - `fetching <url>`
  - `reading cached <filename>`
  - `fetching page <n> of <url>` — one per extra page while following a paginated document
  - `<source> 429, backing off <n>s (attempt <n> of 3)` — while waiting out a rate limit
- **Size per dispatch:** unclear — one cached page, or up to 20 fetches if it follows a paginated document to its end.
- **Dispatch site:** `extract_phase_b.md:60`
- **Concurrency:** **all at once, up to the harness limit `preflight.mjs` reported** — the same rule
  as the Branch Searcher, and for the same reason: nothing here is rate-limited per host, so the only
  bound is how many sub-agents Claude Code will run. Do not invent a smaller batch size.

  > **Peter:** Concurrency is the maximum amount of subagents the system is able to run
- **Missing rules:** none. **CLOSED — the page-quality values now have their own file.** Every
  claims file carries a `pageQuality` — `primary-self`, `primary-3p`, `secondary`, `blog`, `forum`,
  `internal`, `unreliable` — and the schema handed this agent the list without ever saying what one
  meant. The definitions lived in `vetting.md`, which is about people, which this agent does not vet
  and was never sent.

  They now live in **`brain/page_quality.md`**: what the tag is, what it is for, the values with
  their audit scores, and the two that need care (`primary-self` is high and biased at once,
  `internal` sits outside the ranking). Split out rather than folded into this agent's own file
  because three other places read the same definitions — Audit ranks on them, Synthesize drops
  `unreliable` on them, and `vetting.md` names them as the other half of the pair.

  Renamed from *source* quality on the way: `source` already means one of the six in this skill —
  `cache/<source>/`, `sources_unavailable`, one Source Analyst per source — so `sourceQuality` read as
  "how good is Reddit". It is a property of one page. Not *relevance* either: that word is twice taken
  (`relevance` on a candidate URL, `topical_relevance` on a handle) and means how on-topic something
  is, which is a different axis from how much weight it carries.

  > **Peter:** page quality is fine

  - **MISSING — "blocked" and "empty" both look like "found nothing".** A paywalled page, a page

  - **MISSING — nothing strips a page down to its text.** `fetch.mjs` saves the raw page. Nothing

## 4. Source Analyst

- **Purpose:** **[DRAFT]** Read everything one source produced at once and catch what no single-page
  reader can see — the recurring tone, the argument running under several threads, the oddity.

  > **Peter:** Also aggrregate the handlers that belkong to the source and order them
- **Phase:** Extract
- **One dispatch per:** one source that pulled data
- **Full run:** ≤6 (spec — one per source)
- **`--fast`:** ≤6
- **Input**
