# digmore V0.1.1 — sub-agent definitions

Baseline: the skill as built at commit `da94c5a`, read 2026-08-19.

**Square brackets mean it needs Peter.** Nothing else is bracketed.

Needs an answer: **[OPEN]** identified, not decided · **[MISSING]** a capability nothing provides ·
**[TBD]** the skill does not say · **[DRAFT]** written from what the skill does today, for Peter to
replace. Each carries a `> **Peter:**` line to fill in.

Does not: **TO BUILD** decided here, and a skill file still says otherwise · **BUILT** / **DONE** the
skill now matches · **CLOSED** looked at and deliberately left alone · **IN FLUX** being changed
elsewhere right now, so what is written here is provisional · **(spec)** a stated cap ·
**(arithmetic)** caps multiplied, no total is stated.

**TO BUILD and [OPEN] are not the same kind of thing, and it matters.** A **TO BUILD** row is
settled — this file has a position and a skill file has not caught up. It needs an edit, not an
answer, and it becomes **BUILT** once the edit is made. An **[OPEN]** row is one where neither
document has a position yet, so there is nothing for the source-of-truth rule to resolve and a
decision is genuinely owed.

**Purpose** is the first field on every agent: the one job it exists to do, in a sentence. Not when
it runs (**Phase**) and not what one dispatch covers (**One dispatch per**) — why it is a separate
agent at all. The ones still marked **[DRAFT]** are waiting on you; the rest you have answered.

"Sent" means the path is written into the agent's prompt and it opens the file itself.

**This file is the source of truth.** Where it and a skill file disagree, this file wins and the
skill file is what changes. A **TO BUILD** row is not a question — it is a skill file that has not
caught up yet.

### Turning an entry here into a skill file

**Every agent's file under `skill/brain/subagents/` opens with a summary table. `AGENTS.md`
§"Writing a sub-agent file" defines it** — the nineteen fields, their order, and the three rules
that keep it honest. It is not repeated here.

Most of it is already written in each entry below, under a different name:

| This document | The summary table |
|---|---|
| Phase · Purpose · One dispatch per · Run instances · Concurrency | same |
| Input → *Task text* | Input text |
| Input → *Rule files sent* / *Data files sent* | Input rule files / Input data files |

| Log file | Logs |

**Four fields have no answer in this document and must be worked out when the file is written.**
They are the ones worth the most, because each is a failure this design has already had:

- **What it must not do** — the boundary. Its absence is why the Expert Document Analyst existed at
  all, and why the Claim Fact Checker was sent a file that invited it to extract claims.
- **Settings that control it** — scattered across prose today, and each entry has to say whether the
  agent enforces the configuration or the orchestrator counts it. A number an agent cannot act on is a
  number it will misread.
- **Held in its context** — implicit everywhere. It is the field that makes the disk-versus-context
  split checkable rather than assumed.
- **How it reports failure** — stated for some agents, absent for most.

Expect writing these to surface gaps rather than transcribe answers.

**The orchestrator** is the twelfth actor in this document and the only one that is not a
sub-agent: the main session, running the skill from the first phase to the last. It is a worker, not
a wrapper. It talks to the user — the only actor that can — decides the plan, dispatches every agent
below and waits on them, checks what comes back and repairs or drops it, counts the budgets, and
writes every file no single agent owns: `research_plan.json`, `audit.md`, `experts.csv`, the verdicts
in `<source>-handles.json`, and both the rows and the enriched cells in `players.csv`.

It is also the one context that has to survive all six phases, while a sub-agent's dies the moment
it returns. That asymmetry is why the bulk material goes to disk and only receipts come back.

### The stuck-agent check — BUILT

Applies to every agent here, so it sits at the top rather than in one entry.

**The trigger is the heartbeat's modification time, not time since dispatch** — two minutes without
it moving, and ten for the kill. A live agent is never killed for being slow, only for having
stopped. Time since dispatch said nothing useful: an agent twenty minutes into a long branch whose
heartbeat moved ten seconds ago is working, and one that fell over after thirty seconds is not.

**Two minutes is the default because the open web is the slow case** — a request working through its
backoff can honestly hold one line for three minutes, where every scripted source answers in about a
second. **A fast source may set a tighter threshold in its own `subagents/<agent>/<source>.md`, and
that wins for its sub-agents.** Hacker News is the first, at one minute.

### The run log — NEW

**DECIDED — the orchestrator writes one log for the whole run, at the topic root.** Peter: *a main
log with each sub-phase timing, so we can later debug what took longest.*

```
digmore/<slug>/run_log.md
```

At the topic root rather than in `cache/`, which is disposable — this is the only record of where a
run spent its time, and it is read after the run rather than during it.

**One line per step boundary, appended as it happens.** Not when the step finishes: a run that dies
in Vet has to leave a log showing it reached Vet.

An excerpt — the run header and the first three steps. A real file carries a pair per step through to
`[6/6] Audit · done`, then the next run's header:

```
## run 2026-08-21T09:14:02Z — fresh · manual, full · run_history[0]

2026-08-21T09:14:02Z  [1/6]    Plan · start
2026-08-21T09:14:48Z  [1/6]    Plan · done — 1 scoping agent, 5 angles                     +46s
2026-08-21T09:14:48Z  [2.1/6]  Extract · Search · start
2026-08-21T09:19:30Z  [2.1/6]  Extract · Search · done — 25 branch searchers, 302 URLs     +4m42s
2026-08-21T09:19:30Z  [2.2/6]  Extract · Read · start
2026-08-21T10:31:11Z  [2.2/6]  Extract · Read · done — 188 page analysts, 12 blocked       +1h11m
…
```

- **The elapsed figure is the difference from the line above**, so nothing has to be kept in context
  and a partial log still reads correctly.
- **The step name is the marker `reporting.md` already prints**, so the log and the terminal never
  invent separate vocabularies.
- **A `done` line's tail says what the step did** — agents dispatched, and the one count that
  explains the duration. An hour is only debuggable beside the number of things it was doing.
- **Every sub-step gets its own pair**, including each one inside Audit — review, repair, copy edit,
  fact check, annotation — and each wave of Enrichment's Player Profilers. That is where the time
  goes, and a single `Audit` line hides fifty fetching dispatches inside it.
- **A failed or skipped step says so on its `done` line** — `Vet · done — Reddit and Twitter
  unavailable, no API key`. A missing pair reads as a crash, and a skipped phase is not one.
- **The timestamp comes from the shell, never from the model.** You have no clock, and a composed
  stamp makes every elapsed figure wrong. Append through Bash.
- **Append across runs, never replace.** Unlike `audit.md`, which describes one run, this is the
  record of what the topic has cost over its life — and the second run is when the first run's
  timings become useful.
- **Nothing reads it during the run.** It is a debugging artifact, not an input to a decision. The
  stuck-agent check still reads `cache/_progress/*.log`: different question, different time,
  different file.

Knock-ons in the skill: `phases/index.md` §"Where a run writes" gains a layout row and a writer row,
and `reporting.md` gains the rule that every marker it prints is appended here too.

### Resuming a run — read the log first — NEW

**DECIDED — a retry or a re-run reads `run_log.md` to find the phase it stopped in, and re-enters
there.** Peter: *check the main log for the last stage we were at and continue dispatching phases and
sub-agents from that stage — without bloating the orchestrator with files it does not need to read.*

Resume today infers position by comparing `research_plan.json` against the cache and every partial
output across all six phases — a scan of the whole topic directory, all of it into the context that
then has to survive the run. **The saving is the five phases you no longer scan**, not the one you
still do.

**The log gives you the phase; the disk gives you what is outstanding inside it.** Both, in that
order:

| Last line for a phase | What you do |
|---|---|
| `done` | re-enter the **next** phase, without opening the completed one's artifacts |
| `start` with no `done` after it | re-enter **that** phase and run its salvage path from `phases/index.md` |

The second row is why the log cannot replace the disk check: a run killed during Extract · Read wrote
`start` and nothing else, which names the phase and says nothing about which of 188 URLs were read.

**Three rules that keep it honest:**

- **No log, unreadable, or a topic predating this → full scan.** An absent log is no information,
  never evidence that nothing ran.
- **Where the log and the disk disagree, the disk wins.** These lines are written by you rather than
  by a script, so one can be wrong, out of order, or missing because the process died between the
  work and the write. A file that exists exists.
- **Record the resume decision as its own line**, naming the phase re-entered and whether it came
  from a `done` or an unfinished `start`. Otherwise a skipped four-second Extract and a broken one
  look identical.

**It changes nothing about what a phase does on re-entry** — the salvage paths already say how each
picks up. This decides *which* of them runs.

Knock-on in the skill: `phases/index.md` §"Salvage paths on phase failure" opens with the log, keeps
every per-phase path underneath it, and its closing *"Resume infers progress from on-disk state"*
becomes the two-source rule above.

## The Enrichment phase — NEW

**DECIDED — a sixth phase, between Vet and Synthesize.** Peter. The run becomes Plan, Extract, Vet,
**Enrichment**, Synthesize, Audit, and every progress marker renumbers to `[n/6]`.

The phase files are lettered, so two are renamed and one is new:

| Was | Is |
|---|---|
| `phases/synthesize_phase_d.md` | `phases/synthesize_phase_e.md` |
| `phases/audit_phase_e.md` | `phases/audit_phase_f.md` |
| — | `phases/enrich_phase_d.md` |

### Why it exists

Extract collects, Vet judges people, Synthesize writes. **Nothing between them turned what was
collected into the run's subjects** — and that gap is why `players.csv` had no owner: the only step
that ever enumerated players was `landscape.md:80`'s cross-check, which counts mentions in
`raw_research_outcomes.md`, a file written in Synthesize by the old #8, after #6 needs the rows.
(That file is now #7's, written in this phase — but still after the rows, which is why the
count is a script's job rather than a by-product of the writing.)

Enrichment is the phase where the run works out **who this research is about**, using the verdicts
Vet has just produced. It cannot sit inside Extract — the verdicts do not exist yet. It cannot sit
inside Synthesize — the writer needs a finished file to render from.

### What happens in it

**Expert enrichment comes first, and everything after it counts what it added.**

1. **One #2 Branch Searcher per vetted expert**, in its Enrichment mode — an expert is a branch, and
   its source is implied by the handle. It reads that expert's vetting cache, ranks against the
   research question, and returns a URL list. No query: the material is already on disk.
2. **Dedupe**, against the other experts' lists *and* against what Extract already read — an expert
   surfaced because they said something the run read, so their cached comments overlap what is
   already extracted.
3. **One #3 Page Analyst per surviving page**, in its Enrichment mode: carrying the research
   question, keeping only claims that bear on it.
4. **One #4 Source Analyst per source that gained material**, in its Enrichment mode: append the new
   claims, entities and handles to that source's three files, leaving Vet's verdicts untouched.

**Then the player work, unchanged from what was already settled:**

5. **A script filters — `players.mjs candidates --topic <slug>`.** It reads all six
   `full_source_analysis/<source>-players.json`, joins every
   claim's `handle` to its verdict in `<source>-handles.json`, drops what the run does not listen
   to, recounts documents per player across all sources, and applies the 5+ floor. Deterministic:
   same inputs, same candidates, every run.
6. **The orchestrator selects.** It reads the surviving candidates — names, counts and the
   per-source relevance notes, **not claim text** — and decides which become rows.
7. **The orchestrator writes `players.csv`** with the rows and whatever base data it already has.
   Cells that need fetching stay empty.
8. **One #6 Player Profiler per row**, dispatched with that player's claim references.
9. **The orchestrator fills the returned cells** into the rows it already wrote.

**And that is where the phase ends.** The Raw report writer was step 10 here and is now the first
step of Synthesize — see §"Where the Synthesize / Audit seam falls". Enrichment answers *who the
research is about*; turning the evidence into documents is the next phase's job.

**Why the expert work sits at the front.** It changes the claim set, and both the candidate count in
step 5 and the raw report in the phase after count it. Run it later — as `synthesize_phase_e.md` §2
still does — and its claims land after the candidate count and after the raw report, in a directory
nothing reads again. They would reach no report at all.

**Why the raw report waits for this whole phase.** #6 fetches pricing pages and funding announcements
— facts that exist nowhere else in the run and never become claims. A declared enumerable section
wanting a funding round it found could not see it. The raw report itself needs nothing from
`players.csv`; the enumerable sections do, and #7 builds those first.

**DECIDED — accepted, not solved: player-profile findings never enter the claim record.** Peter:
*players information is ranked before we start, and is scrutinised with claims, more online search
and more enriching — this data is quite robust.* Cells carry citations, but they are not claims, so
they are never scored, never ranked and never fact-checked. Recorded so the boundary of the
verification path is visible rather than assumed.

Later steps may be added to this phase; these are the ones settled now.

### Expert enrichment — what is on disk, per source

**DECIDED.** Peter. Selection is free everywhere, because vetting already fetched the material to
judge each expert by. Extraction is free only where that material is complete:

| Source | What vetting already cached | What Enrichment does |
|---|---|---|
| **Reddit** | up to 100 recent comments, full bodies, with subreddits and permalinks | select and extract straight from the cache — no fetch |
| **Twitter** | the sampled posts, **for deep-pass handles only** | expand on deep-pass handles only. Profile-only handles have no posts cached, and in `--fast` there is no deep pass at all |
| **Hacker News** | recent comments **in full**, each carrying the story it sits under | select and extract straight from the cache, and pull the surrounding thread when one is worth reading |
| **Blogs, personal sites, anything off-platform** | nothing | **out of scope.** Not expanded on |

**BUILT — the 280-character cut is gone.** It was ours rather than the API's: Algolia returned each
comment whole and `hackernews.mjs` sliced it before storing, throwing away for free the only thing
Enrichment needs to extract from. 280 characters is enough to judge whether a comment is on-topic and
not enough to quote from, so every usable comment would have cost a thread re-fetch to recover text
we already had.

**And `recent_comments` gained more than the missing text.** Each entry now carries `story_id` and
`story_title` beside the body, so following a comment to its thread needs no lookup — and the shape
matches Reddit's, one object per comment rather than parallel lists.

**BUILT — Hacker News is on Firebase and nothing about it is throttled.** Account age used to come
from the `news.ycombinator.com/user` HTML page at one request per 15 seconds. Firebase serves the
same fields unthrottled and in parallel; the page, its parser and its throttle are gone. Threads and
per-author searches were always on Algolia, which was never rate limited. See #5 for what that
changed in Vet.

**DECIDED — the new handles are not vetted.** An expert's post quotes someone the run has never seen.
Peter: *i am ok with no verdict handles that come from expert enrichment.* They are appended without
a verdict and quoted with the unverified caveat.

One consequence, recorded rather than re-opened: the candidate script counts never-vetted handles
toward the five-document floor, so the expert trail can now create a player on its own.

- **A script owns the deterministic half of #7's job** — the verdict join, the claim filter and the

### What counts, and what is judgement

**Mechanical, in the script — the floor.** A player is a candidate at **5+ documents across all
sources**, counted after the claim filter. One document that names a player counts once, however
many times the name appears in it.

Which claims count:

| Handle verdict | Claims reach the report | Count toward the 5+ |
|---|---|---|
| `legit` | yes | yes |
| `unknown` | yes, caveated | yes |
| **never vetted** — below `vet.handleCapPerSource` | yes, caveated | yes |
| `promoter` | yes, labelled as a promotional signal | **no** |
| `spammer`, `throwaway` | no | no |
| **no handle at all** — websearch, local | yes, filtered on `pageQuality` | yes |

Three of those rows need their reasoning kept:

- **`unknown` and never-vetted count.** An absent verdict means never vetted, not rejected — the
  same meaning as `unknown`. Excluding them would contradict #5's caveat decision, and on Twitter,
  where the heuristic floor never returns `legit`, no player could ever be counted from that source.
- **`promoter` is kept but not counted.** A founder posting about their own product across six
  threads is exactly how a promoter manufactures a player. The quotes still reach the report,
  labelled; they just cannot create a row on their own.
- **Claims with no handle count.** They are most of what is said about a company — vendor pages,
  comparisons, reviews — and Synthesize §1 already filters them on page quality alone. Without them
  a company would be judged on forum chatter.

**The original brain was stricter than all of this**, and it is worth recording why we did not copy
it: §1 Filter there dropped every quote whose verdict was not `legit`, and dropped `forum` sources
from `unknown` handles outright. It also had **no vetting cap** — `vet_phase_b.md` says *"For every
handle seen in Phase A, run `vet_user`"* — so it never had unvetted handles to rule on.
`vet.handleCapPerSource` arrived during the V0.1 review, and #5 has since reversed the `unknown`
rule deliberately.

**Judgement, and whose.** The orchestrator decides **whether players are needed at all** and **which
qualifying candidates become rows**. It holds what that needs: `scope.deliverables` from Plan, the
command's reference file, and the ranked candidate list.

Three bounds on it, because an unbounded judgement here is the failure `Run ceilings` already
records — two real runs applying different caps because the number was prose the model was trusted
to obey, with nothing flagging the difference:

- It may **cut** from the qualifying list. It may **never add** a player below the floor.
- **Every exclusion is recorded with a reason.** `landscape.md:80` already requires this and today
  has nowhere to put it.
- **A run whose declared sections need no players skips selection and profiling entirely.** That is
  the checkable form of "if at all": `gtm` writes no `players.csv` unless chained from a landscape
  parent, and `ask` has an explicit "no players in scope" path.

`enrich_phase_d.md` carries this framing and the inputs. It does **not** carry a per-command table —
`competitor` taking its focal company plus 3–5 nearest peers off the ranked list is one instance of
the judgement above, not a separate rule.

### No configured limit on the row count

**DECIDED.** Peter: *"no limit on row counts, our 5+ mentions and filtering of claim is a good
enough limit."* There is no `synthesize.playersProfiled`, and no `--fast` reduction. The floor plus
the claim filter are the bound, and unlike a fixed cap they scale with how much the run actually
found. This closes the open configuration question in #6.

### What it replaces

**`claims.mjs` is not built.** It was proposed to string-match player names across ~700 claims files
with a soft rule — name, aliases and domain as substrings — that could miss or over-match. Recording
the claim references in `<source>-players.json` at read time removes the matching problem entirely:
the association is written where the evidence is, by the agent that read it. Its two verbs are
absorbed, `entities` by #4 and `slice` by the enrichment script.

## 1. Scoping agent

- **Purpose:** Find out what the subject actually is before the run commits to searching
  it — the words its own people use, the names that keep coming up — and turn that into the angles
  every later search is built on.
