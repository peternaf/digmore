# V0.1.1 run anatomy — the diagram, and how to keep working on it

The diagram is `V0.1.1-run-anatomy.html`, beside this file. Open it in a browser; it needs no
build, no server and no network beyond a Google Fonts stylesheet it degrades without.

This file is the brief. It says what the diagram is for, every direction Peter gave while it was
built, and what is still open — so the next model can continue rather than start again.

## What it is for

**One page that explains a digmore run to someone who has never seen the project.** Not a spec, not
a substitute for `V0.1.1-subagents.md`. A reader should finish it knowing what happens, in what
order, what they personally have to do, and where everything the run produces ends up.

It has a second audience — Peter, scrutinising the structure before it ships — and that is why it
carries the context and file columns. Those exist so a design problem is visible as a shape rather
than as a paragraph.

## What it holds, in order

1. **The flow diagram.** One SVG, five columns, top to bottom.
2. **The persistence chart.** A second SVG: what the main session is carrying, across the six phases.
3. **The sub-agent table.** Plain HTML, twelve columns, one row per agent.

### The five columns

| Column | Holds |
|---|---|
| YOU | The points where the run stops and needs an answer, plus the two ends — asking, and reading the result |
| DIGMORE — ON ITS OWN | Every step it takes without you, grouped by phase |
| MAIN CONTEXT | What that step leaves in the main session |
| SUB-AGENT CONTEXT | What the sub-agent held while it ran, and threw away when it returned |
| FILES | `IN` read · `OUT` written · `NET` fetched over the network |

Encodings: a **dashed box** stops and waits for the user. A **thick left edge** on a DIGMORE box
means a sub-agent did it. Steps with no sub-agent say so in the fourth column rather than sitting
blank.

### The twelve table columns

Number · agent · phase · purpose · instances per run · input text from the main session · input
files the main session passes · what it does · what sits in its context · what it writes back ·
files it writes · what it logs.

## Directions Peter gave, and what each changed

These are the corrections that shaped it. **Treat them as standing constraints, not history** — the
same mistakes are easy to make again.

1. **"I asked for a diagram, not a text report."** The first attempt was a document with phase
   cards, tables and commentary. Cut to the diagram alone. Prose earns its place only where a
   diagram cannot carry it.
2. **"Top to bottom, not right to left."** The flow runs down a single spine. Columns are a *who*
   axis, never a flow axis.
3. **"So many colours and text formats it hurts to look at."** The page is monochrome — ink, grey,
   hairline. No accent colours, no filled section bars, two text sizes, monospace reserved for
   filenames and counts. Distinctions are carried by shape (dashed, thick edge), not hue.
4. **"Write it for someone who doesn't know how digmore is built."** No internal names in the
   diagram: no schema keys, no agent class names, no `<source>-handles.json` in the prose. Say
   "the ranked list of people". Filenames appear only in the FILES column, where they are the point.
5. **"It's not clear what the skill does and what the user does."** That produced the YOU lane.
6. **"Facts file? We have claims files."** Do not coin vocabulary. Use the repo's own word, or plain
   English — never a third thing. "Fact" was also wrong on the merits: these are unverified claims
   until Audit.
7. **"'The same receipt as Read' / 'the gap list from the first pass' make no sense."** Every cell
   must be self-contained. Never point at another row and expect the reader to hold it.
8. **"Why say 'nothing' — what does that tell me?"** An empty answer is not information. Say the
   concrete thing that does arrive, and where genuinely nothing does, say what the step spends
   instead.
9. **"That column is the orchestrator's context — a sub-agent line does not belong there."** Which
   split MAIN and SUB-AGENT into two columns. Do not merge them back.
10. **"I preferred the lighter bars."** The persistence chart is one bar tone. An earlier version
    used a second, darker tone for the two heaviest items; it inverted in dark mode and was
    redundant with the size note under each label.
11. **"Store it in the repo — I don't want to open an Anthropic URL."** Hence the standalone file.

## The one thing that was wrong, and is now stated

Peter asked what the bars that start and end mid-chart meant — *"I didn't know this is even
possible."* He was right to.

**A bar's end is not a deletion.** Nothing leaves a session transcript; it only grows. The bar marks
an item's **useful life** — from the phase it enters the main session to the last phase that reads
it. The end is worth drawing for three reasons, and the chart now says so:

- it is what a **resumed run** must rebuild from disk, having no transcript;
- it is what a **compaction** could safely drop;
- an item needed late but held only from early on is a fragile dependency, and shows up as a long bar.

**The bar ends are a reading, not spec.** They were derived by finding the last step that consumes
each item. `V0.1.1-subagents.md` states no lifetimes. Several items are also written to disk, so the
main session's copy is redundant and could in principle end earlier.

## Where the content came from

Drawn from `V0.1.1-subagents.md` and `skill/brain/` as of 2026-08-22. Where the two disagreed, the
subagents doc won — it declares itself the source of truth.

Three things are marked undecided in the diagram because they are undecided in the doc:

- the **Raw report writer's return shape** — a receipt is proposed, the fields are not settled;
- the **Brief Reviewer's log**, and the **Copy Editor's log** — neither returns a schema, so neither
  gets the dispatch template, and the heartbeat instruction lives in that template.

Two more, noticed while drawing, not yet resolved anywhere:

- the **Source Analyst has no log** and is the longest read in the run. The doc carries Peter's note
  asking for one.
- the **findings are returned in full and also written to the summary**, uncapped — the last place
  the file-first arrangement bends.

## Keeping it true

The diagram is a snapshot and will drift. When the skill or the subagents doc changes, the parts
most likely to go stale, in order:

1. **The phase count and their names.** It has already gone four → five → six. The header, every
   phase band, the `[n/6]` markers and the persistence chart's column count all move together.
2. **The agent roster.** Thirteen became eleven. Agents merge and split.
3. **Cache filenames.** They gained source prefixes (`reddit-vet-<name>.json`) partway through.
4. **Ceilings.** They live in `skill/scripts/config.mjs`; the diagram quotes a few by value.

## Editing the HTML

Full mechanical notes are in the comment at the top of the file: column x-origins, box heights, the
line-break budget per column, the persistence-chart bar arithmetic, and the theme-token rule.

The one thing to know before opening it: **the SVG has no layout engine.** Every element is
absolutely positioned, text does not wrap, and each visual line is its own `<text>`. Adding a row
means moving everything below it.

If that becomes the bottleneck, the honest next step is to move the row data into a small JSON file
and generate the SVG from it — the content is regular enough. That was deliberately not done here:
it is a second thing to keep in step, and the diagram was still changing shape every pass.
