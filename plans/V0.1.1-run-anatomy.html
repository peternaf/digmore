Anatomy of a Digmore Run

V0.1.1 — six phases, eleven agents

Digmore is a research tool that runs inside Claude Code. You give it a topic; it searches the web, reads what it finds, checks who wrote it, and hands back a report where every claim names its source. Five columns: what you do, what it does alone, what the main session ends up holding, what the sub-agent held and threw away, and which files each step touches.

dashed — it stops and waits for you thick left edge — a sub-agent main context — survives to the end of the run sub-agent context — dies the moment it returns IN / OUT / NET — files read, written, fetched

Every path is under digmore/<topic>/. Not listed per row, because every dispatched sub-agent writes them: a heartbeat line to cache/_progress/<label>.log before each step, and a copy of its answer to cache/_returns/<label>.json.

What the main session is carrying, phase by phase

The third column above is one step at a time. This is the same thing across the whole run: a bar covers the phases in which that item is still being used. Nothing is ever deleted from a session — the transcript only grows — so a bar ending means the last step that reads that item has passed, not that the room is handed back. Where the bars end is therefore where a compaction could safely drop something, and what a resumed run has to rebuild from the files instead.

Two agents account for nearly all the reading. The Source Analyst opens everything one site produced and returns nothing at all — it writes three files instead. The Raw report writer then opens only those six reports, not the seven hundred claims files behind them. That pair is what replaced a single agent opening every claims file in the topic.

The one place the arrangement still bends: the findings are written to the summary file and also returned in full, uncapped, so the main session carries a second copy of the report's substance from Synthesize to the end of the run.
